3.1 颜色模型基础

为什么需要 4 种颜色空间？它们各自擅长什么？色盲眼中看到的世界又是什么样？

1 原案例

本章从头到尾只用一份数据：美国各州犯罪统计（data/crime.csv），含 50 个州、13 列（人口、抢劫、谋杀、纵火等）。数据本身不是重点 —— 重点是同一份数据换一套配色，读者对它的理解会完全不同。

本章的 4 个配色问题，对应 4 个知识块
问题在哪一节回答关键结论
颜色能不能直接拿 RGB 插值？3.1 / 3.3不行，RGB 不感知均匀，要在 CIE Lab 里插值
连续数值该用哪类色阶？3.2有序 → 顺序型；有中点 → 发散型；无序 → 定性型
几个类别、怎么搭色不刺眼？3.4 / 3.7≤ 7 类；色相拉开 ≥ 30°；配套色 S 30–50%
色盲读者还看得懂吗？3.5 / 3.8用 CVD 模拟自查；红绿对比最危险

例如把每个州的 murder（谋杀案数）画成柱状图：用「浅蓝 → 深蓝」读者能读出大小；用「红 → 黄 → 绿」的彩虹色阶，读者只会看到花花绿绿 —— 中间的黄色既不是「最大值」也不是「最小值」，它什么语义都没有。

2 嵌入理论

四种颜色空间，四种「擅长」

空间模型擅长是否感知均匀
RGB加色（三束光相加）屏幕发光原理、设备原生存储✗ 不是
HSL色相 / 饱和度 / 亮度人（尤其是设计师）的直觉调色✗ 不是
CIE LabL* 明度 + a* / b* 对立通道度量「看上去差多少」✓ 是（黄金标准）
CMYK减色（油墨吸收光）印刷 / 出版✗ 不是

核心结论：RGB 是「设备空间」，Lab 是「思考空间」。设计 colormap 时在 Lab 中插值，转成 RGB 显示时再 clamp —— 这就是为什么 d3.interpolateLab 出来的渐变比 d3.interpolateRgb 平滑。

CVD（色觉缺陷）：约 8% 男性、0.5% 女性存在色觉缺陷。常见三种：红色盲（protanopia，约 1% 男性）、绿色盲（deuteranopia，约 6% 男性，最常见）、蓝色盲（tritanopia，极罕见）。也就是说，一页幻灯片大概率至少有一位读者看不出红绿差别。

3 ⭐ 关键代码
① RGB → HSL 手写：最大通道决定色相 
// 输入 0-255，输出 h∈[0,360) s,l∈[0,100]
function rgbToHsl(r, g, b) {
  r /= 255; g /= 255; b /= 255;
  const max = Math.max(r, g, b), min = Math.min(r, g, b);
  let h, s, l = (max + min) / 2;
  if (max === min) { h = s = 0; }          // 灰：无色相
  else {
    const d = max - min;                     // 相减 → 饱和度
    s = l > 0.5 ? d / (2 - max - min) : d / (max + min);
    switch (max) {                          // 谁最大 → 决定色相落点
      case r: h = (g - b) / d + (g < b ? 6 : 0); break;
      case g: h = (b - r) / d + 2; break;
      case b: h = (r - g) / d + 4; break;
    }
    h /= 6;
  }
  return [h * 360, s * 100, l * 100];
}

自己写一遍，是为了看清三步物理含义：最大通道决定色相、最大减最小决定饱和度、最大加最小决定亮度。也顺带解释了为什么色相是 0–360° 的环形量 —— 加偏移必须 (h + 30 + 360) % 360 才不会出走。

② CVD 模拟：一行矩阵乘法换一双眼睛 
// Machado 2009 一类近似矩阵：把 RGB 乘一遍矩阵即得「色盲眼中」的颜色
const CVD_MATRICES = {
  protanopia:   [[0.567, 0.433, 0], [0.558, 0.442, 0], [0, 0.242, 0.758]],
  deuteranopia: [[0.625, 0.375, 0], [0.700, 0.300, 0], [0, 0.300, 0.700]],
  tritanopia:   [[0.950, 0.050, 0], [0, 0.433, 0.567], [0, 0.475, 0.525]],
};

function simulateCVD([r, g, b], type) {
  const m = CVD_MATRICES[type];
  return [
    r * m[0][0] + g * m[0][1] + b * m[0][2],
    r * m[1][0] + g * m[1][1] + b * m[1][2],
    r * m[2][0] + g * m[2][1] + b * m[2][2],
  ].map((v) => Math.max(0, Math.min(255, v)));
}

三种色觉缺陷都是线性变换：正常视觉的三个锥细胞响应被「合并」了。看矩阵就知道为什么绿色盲最危险 —— 第一行 0.625 / 0.375 与第二行 0.700 / 0.300 几乎相同，红与绿被投影到几乎同一个方向。

③ 本站做法：颜色一律从设计令牌读取 
// 本站零构建、离线可用，所以不引 D3 / 任何颜色库；
// 需要「真实的颜色数值」时，从 CSS 设计令牌里读出来再算。
const token = (name) =>
  getComputedStyle(document.documentElement).getPropertyValue(name).trim();

const rgb = parseColorCss(token('--c-primary'));   // → [67, 56, 202]
const hsl = rgbToHsl(...rgb);                      // 接着做色相旋转、Lab 换算…

好处有三：① 页面里不出现写死的色值，换肤只改 tokens.css；② 深色模式切换后，演示自动跟着变（令牌在深色下是另一套值）；③ 演示与正文图形共用同一套色板，讲的和看到的完全一致。

4 可运行演示

四块面板对应四种颜色空间，点哪一块，右侧就读出该空间的数值与适用场景：在 RGB 立方体上点面选色、拖动「方位角」旋转投影、在 HSL 轮盘上点角度换色相、在 a*b* 平面上点位置换色 —— 四处改的是同一个颜色。

本节小结

  • RGB 是设备空间、HSL 是直觉空间、CIE Lab 是感知空间、CMYK 是印刷空间 —— 设计 colormap 要在 Lab 里插值。
  • 色相是 0–360° 的环形量，任何加偏移都要 mod 360；饱和度由「最大减最小」决定。
  • 约 8% 男性有色觉缺陷，其中绿色盲最多 —— 配色必须过 CVD 这一关（3.8 有模拟器）。
自测 · 1 题

要设计一条平滑、明暗过渡自然的 colormap 渐变，应该在哪个颜色空间里做插值？

RGB 与 HSL 都不是感知均匀的：在 RGB 里线性插值，中段会出现「看着比两端都更暗/更亮」的假台阶。CIE Lab 的欧氏距离 ≈ 人眼感知差，所以在 Lab 里等步长插值得到的渐变，人眼看着才是等步长的 —— 这就是 d3.interpolateLab 存在的理由。

3.2 colormap 三类选择

顺序型 / 发散型 / 定性型 —— 选错类型不是「不好看」，而是误导读者。

1 原案例
三类 colormap 对应三种数据语义
类型数据语义颜色特征典型方案
顺序型 Sequential有自然顺序：人口、温度、谋杀案数亮度单调 + 色相单调Viridis / Plasma / Cividis
发散型 Diverging有真有意义的中点：0、正负偏差、相对中位数两端异色、中间最浅RdBu / BrBG / PiYG
定性型 Qualitative无序类别：州、产品线、实验分组色相区分大、亮度接近Tableau10 / Set1 / Okabe–Ito

回到 crime.csv：murder 是「有自然顺序」的数值 → 顺序型；如果先算出「各州谋杀率与本州历史均值的差」，差值有正有负、0 有意义 → 发散型；如果只是想区分 5 个地区的类别 → 定性型。

2 嵌入理论

选错类型 = 撒谎

用发散型 RdBu 去画有序的「50 州谋杀率」：色阶中段接近白色，读者会本能地把「接近白色」的州读成「中间的、正常的」—— 可 100 这个数值没有任何语义，纯属误导。反过来，用顺序型 Viridis 去表示正负偏差，读者会以为白色的地方是零点，而 Viridis 的中点其实是深紫色。所以先问数据语义，再挑色阶类型。

CVD 友好检查清单：Viridis / Cividis ✅ 优（Nature Methods 推荐）；RdBu / BrBG △ 中等（红绿两端对色盲不友好）；Tableau10 △ 与色相相关；Jet / Rainbow ⚠ 直接禁用。

3 ⭐ 关键代码
① 三类 scale 速记 
// 顺序型：[0, 1] → 颜色（单调亮度）
const seq = d3.scaleSequential(d3.interpolateViridis);

// 发散型：t=0 一端、t=0.5 中点、t=1 另一端
const div = d3.interpolateRdBu;

// 定性型：类别 → 颜色（互不相邻才不打架）
const cat = d3.scaleOrdinal(d3.schemeTableau10);

三者的接口完全一样（输入 [0,1] 出颜色），区别只在语义契约：顺序型承诺「越大越深」，发散型承诺「中点最浅」，定性型承诺「亮度接近」。一旦把某个契约用在了不满足前提的数据上，颜色就开始说谎。

② 决策表：先问数据，再挑色阶 
function pickColormap(data) {
  if (data.hasMeaningfulMidpoint) return 'diverging';   // 有真中点（0 / 均值）
  if (data.isOrdered)              return 'sequential';  // 有自然顺序
  return 'categorical';                                  // 其余：无序类别
}

两个问题的顺序不能颠倒：「0 有没有意义」要先于「数据有没有顺序」。有顺序、但中点为 0 的数据（如环比增长）应当走发散型 —— 这正是 crime.csv 的谋杀率与「谋杀率偏差」的分水岭。

③ 本站做法：用令牌混色算出渐变 
// 顺序型：从「主色 5% + 表面色 95%」走到「主色 100%」，逐级混色
const cells = 16;
for (let i = 0; i < cells; i++) {
  const p = Math.round(i / (cells - 1) * 100);
  strip.append(el.style.background =
    `color-mix(in srgb, var(--c-primary) ${p}%, var(--c-surface))`);
}

// 发散型：左半段 危险色 → 表面色，右半段 表面色 → 主色
// 中点天然落在「表面色」，与「中点 = 0」的语义吻合

为什么不用写死的 hex 数组：本站要支持深浅色主题。var(--c-primary) 在白底是靛蓝、在深底是淡靛蓝，var(--c-surface) 也跟着换 —— 混色算出来的整条色阶自动适配主题，硬编码的 hex 做不到这一点。

4 可运行演示

上方是计算出来的三条对照条（顺序与发散型由令牌混色逐级生成，不是图片）；下方把 crime.csv 的谋杀案数画成真实柱状图，切换「顺序型 / 发散型」看发散型是怎么把有序数据讲错的。

本节小结

  • 三类 colormap 各对应一种数据语义：有序 → 顺序型、有真中点 → 发散型、无序类别 → 定性型。
  • 选错类型不是审美问题：发散型画有序数据会凭空造出一个「正常的中点」，顺序型画正负偏差会让人误把深紫当零点。
  • 彩虹型（Jet）三类都算不上：非感知均匀、CVD 不友好、打印也不友好，应当直接禁用。
自测 · 1 题

有一份数据是「各州犯罪率相对全美中位数的偏差」（有正有负，0 是有意义的中点），最合适的 colormap 类型是？

偏差数据的「中点 0」有明确语义，所以要用发散型：中点最浅、两端异色，读者一眼就能看出「高于中位数」还是「低于中位数」以及偏离的幅度。顺序型会把 0 藏在色阶中段，定性型则丢掉了正负的程度信息。

3.3 CIE Lab 色域图

在感知均匀的颜色空间里，「能显示的颜色」到底长什么样？

1 原案例

给 crime.csv 配一条「高饱和的纯绿 → 纯红」色阶。在 Lab 里算出来的颜色很漂亮，但 LCD 屏幕上显示出来的绿却「闷」了一截 —— 因为算出来的那个绿已经跑出屏幕的色域了。

色域标准 / 场景相对大小本课用途
sRGBWeb / PPT / 一般科研图最小（基准）本次重构的目标色域
Adobe RGB摄影 / 印刷中（绿域更宽）投稿印刷版时需注意
Rec.20204K / HDR 电视最大目前 Web 用不到
2 嵌入理论

为什么是「嵌套」，为什么会被 clamp

三个色域是包含关系：sRGB ⊂ Adobe RGB ⊂ Rec.2020。用 Lab 坐标算出来的颜色如果落在 sRGB 之外，标准转换流程会把它夹（clamp）回 sRGB 边界 —— 结果不是报错，而是「颜色看起来变了」，而且是在毫无察觉的情况下变。

实战三条：① d3.lab(L, a, b).rgb() 会静默 clamp；② 设计 colormap 用 d3.interpolateLab，比 interpolateRgb 平滑；③ 高饱和色只在打印 / 4K 屏幕上「真的存在」，Web 上看不一定准。

3 ⭐ 关键代码
① Lab ↔ sRGB：不 clamp，才能判断出没出色域 
// γ 解码：sRGB 数值 → 线性光
const toLinear = (v) => (v /= 255) <= 0.04045
  ? v / 12.92 : Math.pow((v + 0.055) / 1.055, 2.4);

function labToRgb(L, a, b) {
  const fy = (L + 16) / 116;                     // Lab → XYZ（D65 白点）
  const fx = a / 500 + fy, fz = fy - b / 200;
  const xyz = [fx * fx * fx * 0.95047, fy * fy * fy, fz * fz * fz];
  // XYZ → 线性 RGB（标准 sRGB 矩阵的逆）
  const lin = xyzToLinearSrgb(xyz);
  // 注意：这里故意【不】clamp —— 越界值保留原样，才能判断是否超色域
  return lin.map((v) => v <= 0.0031308
    ? v * 12.92 : 1.055 * Math.pow(v, 1 / 2.4) - 0.055) .map((v) => v * 255);
}

关键就在「不 clamp」这一步。如果转换函数内部先把结果夹到 [0,255]，就永远发现不了算出的颜色已经跑出 sRGB。本站演示用「不 clamp 的转换 + 之后再判断」来找出色域边界，画出的那条边界线就是这样求出来的。

② 判断是否在色域内（顺便求出边界） 
// 在色域内 ⟺ 三个通道都落在 [0, 255]（留一点浮点容差）
const inGamut = (rgb) => rgb.every((v) => v >= -0.5 && v <= 255.5);

// 边界怎么求：固定 L*，沿每个色相角二分手找「最远的仍在色域内的半径」
function outline(L, angles = 180) {
  const pts = [];
  for (let i = 0; i < angles; i++) {
    const th = i / angles * Math.PI * 2;
    let lo = 0, hi = 200;                 // 二分 18 次足够定位
    for (let k = 0; k < 18; k++) {
      const mid = (lo + hi) / 2;
      if (inGamut(labToRgb(L, mid * Math.cos(th), mid * Math.sin(th)))) lo = mid; else hi = mid;
    }
    pts.push([lo * Math.cos(th), lo * Math.sin(th)]);
  }
  return pts;                                  // 连起来就是色域多边形
}

同一个 labToRgb + inGamut 组合能干三件事：判断某个色能不能显示、求出色域边界形状、比较 sRGB 与 Adobe RGB 的大小差（演示里三层嵌套轮廓就是这么来的）。

③ 在 Lab 空间插值 vs 在 RGB 空间插值 
// ✅ 在 Lab 空间插值：中间点感知上是「真正的中间」
const mid = rgb2lab(mix(rgb2lab(c1), rgb2lab(c2), 0.5));

// ❌ 在 RGB 空间直接线性插值：中段会瘪下去（看着更暗）
const bad = [c1, c2].map((c, i) => c * (1 - i) + c * i);

// d3 里对应的两个函数（c1、c2 为任意两端色）
// d3.interpolateLab(c1, c2)(0.5)   ← 感知均匀
// d3.interpolateRgb(c1, c2)(0.5)   ← 不是感知中点

演示里的三层色域、色域内的色块阵列，全部是实时算出来的（不是图片），所以拖动 L* 时能看到色域面积整体收缩 —— 这正是「暗色的可饱和范围更窄」这句话的视觉证据。

4 可运行演示

拖动 L* 滑块看色域收缩；用鼠标在图上拖那个取样点，右侧会实时读出它的 Lab 值与「在不在 sRGB 内」；勾选外两层可以看 Adobe RGB / Rec.2020 的相对大小。

本节小结

  • 色域是嵌套的：sRGB ⊂ Adobe RGB ⊂ Rec.2020；Lab 里算出来的颜色可能落在 sRGB 之外。
  • 超出 sRGB 的颜色会被静默 clamp 回边界 —— 不报错，只是「悄悄变了色」。
  • 想要平滑渐变就在 Lab 里插值，转 RGB 显示时再让浏览器去 clamp；判断「能不能显示」必须先做不 clamp 的转换。
自测 · 1 题

在 Lab 空间里构造一个高饱和纯绿（超出 sRGB），再转成 RGB 显示在一台普通 LCD 上，会发生什么？

转换流程把每个通道夹进 [0, 1]，超出的那部分直接丢掉 —— 于是「超饱和的绿」变成了「sRGB 能表现的最饱和的绿」。它不报错，所以只能靠本节的色域图提前发现：绿色的取样点越出了 sRGB 轮廓。

3.4 色系搭配规则（5 大类）

单色 / 类比 / 互补 / 三等分 / 分裂互补 —— 什么时候该用哪一个？

1 原案例

还是 crime.csv：打算把「东部 / 中西部 / 南部 / 西部」四个地区画成四组柱状图。四个类别、没有顺序 —— 这就要在色轮上「挑角度」了：挑错角度，四组柱子会互相打架；挑对角度，一眼就能对上图例。

规则色相关系特点什么时候用
单色 Monochromatic同一色相，只改亮度 / 饱和度最安全、最不刺眼严肃科研图（Nature 经济型配色）
类比 Analogous色轮相邻 ±30°和谐，但对比度弱表达「层级 / 分组」
互补 Complementary色轮对面 180°对比最强，容易刺眼突出重点：实验组 vs 对照组
三等分 Triadic色轮 120° 等分三种色互相都分得开正好 3 个类别
分裂互补 Split对面两侧 150°互补的温和版拿不准时的默认选择
2 嵌入理论

挑完角度，还得过「可读性」这一关

颜色搭配好不好看，是色相差的问题；文字读不读得清，是对比度的问题 —— 后者可以用 WCAG 的对比度公式量化：对比度 = (L1 + 0.05) / (L2 + 0.05)，其中 L 是相对亮度。

WCAG 2.1 等级正文（约 14px 常规）大字号（≥18.66px 粗体 / ≥24px）
AA≥ 4.5 : 1≥ 3 : 1
AAA≥ 7 : 1≥ 4.5 : 1

最容易踩的坑：把「互补色」直接拿来当「文字色 + 底色」。互补色相差 180°，但两者的亮度可能非常接近 —— 色相差再大，对比度也可能只有 2:1，读起来糊成一团。色相差管「分不分得开」，亮度差管「读不读得清」。

3 ⭐ 关键代码
① 5 大色系的本质：一组色相偏移量 
const HUE_OFFSETS = {
  monochromatic: 0,    // 同色相，只改 S / L
  analogous:     30,   // 相邻 ±30°
  triadic:       120,  // 三等分
  split:         150,  // 分裂互补
  complementary: 180,  // 对面
};

function swatches(baseH, offset, n = 5) {
  return Array.from({ length: n }, (_, i) => {
    const h = (baseH + i * offset + 360) % 360;   // ← mod 360 不能漏
    return hsl2rgb(h, 60, 55);                     // 转成 RGB 直接画

五种规则其实只有一个参数不同：相邻两色的色相差。记住这句，就不用背五段代码了 —— 0 / 30 / 120 / 150 / 180 就是全部。

② WCAG 对比度：把「读不清」变成一个数 
// 相对亮度：先 γ 解码，再加权求和（人眼对绿最敏感）
function luminance([r, g, b]) {
  const lin = [r, g, b].map((v) => {
    v /= 255;
    return v <= 0.03928 ? v / 12.92 : Math.pow((v + 0.055) / 1.055, 2.4);
  });
  return 0.2126 * lin[0] + 0.7152 * lin[1] + 0.0722 * lin[2];
}

// 对比度比值：永远是「亮的在上」，所以结果 ≥ 1
const ratio = (c1, c2) => {
  const [a, b] = [luminance(c1), luminance(c2)].sort((x, y) => y - x);
  return (a + 0.05) / (b + 0.05);
};

三个阈值记牢就够了：3 : 1（大字号 AA / 图形元素边界）、4.5 : 1（正文 AA）、7 : 1（正文 AAA）。演示里的判定就是拿这三个数去比。

③ 用对比度反过来约束配色 
// 先按色系规则生成候选色，再用对比度筛掉不能当文字的那些
function pickTextColor(bg, candidates) {
  const ok = candidates.filter((c) => ratio(bg, c) >= 4.5);
  if (ok.length) return ok[0];
  // 一个都不合格 → 不换色，而是换底色（或改用大字号 + 加粗）
  return null;
}

配色流程应该是「先定语义色相，再按对比度收敛」。反过来的做法（先挑好看的颜色、读不清再说）在演示里一算就知道：很多「好看的互补配」正文对比度只有 2～3:1。

本节小结

  • 5 大色系规则只差一个参数：相邻色相差 0 / 30 / 120 / 150 / 180，对应单色 / 类比 / 三等分 / 分裂互补 / 互补。
  • 选择原则：严肃科研用单色、分组用类比、突出重点用互补、正好 3 类用三等分、拿不准用分裂互补。
  • 色相差决定「分不分得开」，亮度差决定「读不读得清」；正文 AA 门槛是 4.5 : 1，大字号是 3 : 1。

3.5 科研经典配色

Wong / Paul Tol / Okabe–Ito / Tableau / Paired / Viridis —— 顶刊到底在用哪一套？

1 原案例

2 嵌入理论

顶刊选配色的三条硬指标

  • 类别数 ≤ 7：超过 7 种，眼睛就分不清了 —— 类别多时应改画连续 colormap 或做小多图。
  • 过 CVD 模拟：在红色盲 / 绿色盲 / 蓝色盲三种视角下都还能区分（见 3.8）。
  • 灰度可辨：论文常被黑白打印，把颜色转成明度后依然要能区分。这一条排除了大量「色相不同、亮度相同」的漂亮色板。

所以 Okabe–Ito / Wong 这类色板看起来「不够鲜艳」，恰恰是为了满足上面三条：色相拉开的同时，明度也刻意拉出梯度。

3 ⭐ 关键代码
① 用令牌而不是写死 hex 定义色板

色板本身也变成「令牌的组合」，好处是深浅主题一键切换：深色模式下 --ch-1..8 是专门提亮过的一档，浅底能看的色板在深底往往偏暗 —— 用令牌就自动解决了。

② 灰度友好性自检：转成明度排序 
// 把色板里的每个颜色按 WCAG 相对亮度排序，
// 再看「相邻两个的亮度差」是否足够 —— 差太小 ⇒ 黑白打印后糊成一团
const lums = palette.map(luminance);

luminance() 就是 3.4 里那个 WCAG 公式：一个函数，两处用 —— 判断文字对比度、判断灰度打印可辨性。这也是「顶刊配色看起来朴素」的原因：它们为了亮度差，牺牲了一部分色相自由度。

③ 类别数超限时的退路 
// 类别数 ≤ 7：用定性色板；8~10：勉强用定性色板但必须过 CVD；
// > 10：改用「连续 colormap + 排序」或小多图，别硬塞颜色
function paletteFor(n) {
  if (n <= 8) return { type: 'qualitative', note: '过 CVD 与灰度自检即可' };
  if (n <= 12) return { type: 'qualitative+', note: '勉强，建议先合并类别' };
  return { type: 'redesign', note: '改连续 colormap / 小多图 / 分组' };
}

不要为了「每个类别一个颜色」硬撑。更好的做法是：把次要类别合并成「其他」、把一张图拆成小多图、或者干脆让类别映射到位置（分面）而不是颜色。

本节小结

  • 顶刊三条硬指标：类别数 ≤ 7、过 CVD 模拟、灰度打印仍可辨 —— 满足这三条的色板看起来都「不那么鲜艳」。
  • Okabe–Ito / Wong / Paul Tol 是科研场景的三大黄金标准；Tableau 10 好看但红绿不友好；Paired 12 色已过载。

顶刊普遍改用 Okabe–Ito / Wong 这一类「看起来偏朴素」的色板，最核心的原因是？

这类色板在设计时就同时约束了色相差异与明度梯度：色相拉开保证 CVD 读者能区分，明度拉开保证转成灰度后仍能区分。它们在屏幕上确实不如彩虹「抢眼」，但在一页可能被黑白打印、被色觉缺陷读者阅读的论文里，这两个约束比「好看」重要得多。

同一份数据、两种配色 —— 点一下切换，亲眼看看错误的配色是怎么把数据讲错的。

1 原案例

用 crime.csv 里 8 个州的谋杀案数画柱状图，数据不变，只换配色方案：

2 嵌入理论

为什么「彩虹」会被顶刊直接禁用

彩虹色阶的色相是循环的，而人眼在蓝→绿→黄这一段的明度感知并不单调：同一条平缓上升的数据，用彩虹画出来会在中段出现一截「看起来更亮」的假台阶。读者会把这条假台阶当成「数据在这里发生了突变」—— 图制造了数据里并不存在的结构，这比「不好看」严重得多。

教学要点：光看理论不如下场选错一次。本节演示故意提供三种错方案供切换，每一次都指出「错在哪」—— 亲手看到红绿在绿盲模拟下糊成一片，比读一百遍规则都记得住。

3 ⭐ 关键代码
① 错误示范：彩虹色阶（故意写错）

//   它的毛病不是难看，而是感知不均匀 —— 会在数据平缓处造出假的亮台阶。
const rainbowAt = (t) => {
  const h = t * 320;                 // 0° 红 → 320° 紫

// 12 色过载同理：色相平均切 12 份，人眼已经分不清相邻两色

Nature 系列期刊禁用 rainbow / Jet 色阶，最根本的原因是？

彩虹色阶的明度感知不单调（蓝→绿→黄那一段尤其明显），于是「颜色看起来更亮」不等于「数值更大」。读者会把假的亮度台阶读成真实的结构变化 —— 图在制造数据里不存在的信息，这属于学术诚信问题，而不只是审美问题。CVD 与打印问题则是它的附加缺点。

3.7 鲜艳 + 低饱和 哲学生成器

颜色数量 ≤ 7、鲜艳色相 + 低饱和度 —— 好看，而且耐看。

1 原案例

给 crime.csv 的五个地区各配一个色，还想让整套图看起来「有设计感」。把饱和度全开（S=100%）会刺眼，全部低饱和又会发灰 —— 于是有了本章这套经验规则：

规则参数为什么
数量少颜色数 ≤ 7超过 7 种，眼睛就分不清相邻类别了
色相拉开相邻色相差 ≥ 30°用色相拉开「类间距离」，类别才跳得出来
饱和度压低配套色 S = 30–50%每个色都别太「冲」，整页才耐看
主色略艳主色 S = 70–80%鲜明但不刺眼，承担「主角」
高亮极淡高亮 L = 85–90%用于背景、注释、参考线
2 嵌入理论

7 色生成规则：一条「主色 + 两个邻居 + 一个对面 + 一档高亮」的配方

主色 + 2 个类比（±30°）+ 1 个类比低饱和 + 1 个互补 + 1 个互补低饱和 + 1 个高亮 = 7 色。它同时满足了「≤ 7」与「色相拉开 ≥ 30°」，而低饱和的那几档负责把整个页面「压住」，让主色更抢眼。

为什么要分主色 / 配套色：一张图里真正需要「跳出来」的通常只有一两个系列，其余都是陪衬。让所有颜色都鲜艳，等于没有重点；让所有颜色都低饱和，等于没有重点 —— 主次分明才好看。

3 ⭐ 关键代码
① 7 色生成规则 
// 输入基准色相 H、主色饱和度 S、主色亮度 L，输出 7 色（S / L 会被分档调整）
function genPalette(H, S, L) {
  const rotate = (d) => (H + d + 360) % 360;   // 色相安全循环
  const s = (k) => Math.max(0, Math.min(100, S * k));
  const l = (k) => Math.max(0, Math.min(100, L * k));
  return [
    hsl2rgb(rotate(-30), s(0.6), l(1.10)),   // 类比 1 · 低饱和
    hsl2rgb(rotate(-30), s(1.0), l(1.00)),   // 类比 1
    hsl2rgb(H,            s(1.0), l(1.00)),   // 主色 ★
    hsl2rgb(rotate(30),  s(1.0), l(1.00)),   // 类比 2
    hsl2rgb(rotate(30),  s(0.6), l(1.10)),   // 类比 2 · 低饱和
    hsl2rgb(rotate(180), s(0.8), l(0.95)),   // 互补 · 强调
    hsl2rgb(H,            s(0.2), l(1.40)),   // 高亮（极低饱和）
  ];
}

配方里每个颜色都由 (色相偏移, 饱和系数, 亮度系数) 三元组决定 —— 改这三个系数就能整批调色。注意 rotate()：色相是环形的，加偏移必须 mod 360，否则会出现负角度或超过 360 的非法值。

② HSL → RGB 与 hex 输出 
// 标准 HSL → RGB（s,l 是百分数）
function hsl2rgb(h, s, l) {
  s /= 100; l /= 100;
  const k = (n) => (n + h / 30) % 12;
  const a = s * Math.min(l, 1 - l);
  const f = (n) => l - a * Math.max(-1, Math.min(k(n) - 3, Math.min(9 - k(n), 1)));
  return [f(0) * 255, f(8) * 255, f(4) * 255].map((v) => Math.round(v));
}

// 给「复制 hex」用：转成 #rrggbb 文本
const hexOf = ([r, g, b]) =>
  '#' + [r, g, b].map((v) => v.toString(16).padStart(2, '0')).join('');

async function copyAll(hexes) {
  const text = hexes.join(', ');

  }
}

navigator.clipboard 只在安全上下文（https 或 localhost）可用；本地用 file:// 打开页面时它会直接抛错。三层防护（API → execCommand → 可选中文本框）保证任何环境下都不会「点了没反应」。

4 可运行演示

拖动基准色相偏移 / 饱和度 / 亮度三个滑块，右侧实时生成 7 色方案、列出每个色的 hex，并用这套色在真实图表上画一遍。点「复制全部 hex」把 7 个值一次性拿走（自动复制失败时会给出可手动复制的文本框）。

本节小结

  • 7 色配方 = 主色 + 2 类比（±30°）+ 1 类比低饱和 + 1 互补 + 1 互补低饱和 + 1 高亮。
  • 「鲜艳 + 低饱和」的要点是分档：主色艳、配套色淡，主次分明才既好看又耐看。
  • 色相偏移必须 mod 360；生成结果导出为 hex，但页面本身仍应使用令牌以保证主题适配。
自测 · 1 题

按「鲜艳 + 低饱和」的配色哲学，成套方案里的配套色饱和度建议控制在什么区间？

配套色是陪衬，S 控制在 30–50%：既不至于灰到看不出色相，又不会和主色抢注意力。70–80% 是主色的档位，90–100% 会刺眼 —— 一页全是高饱和色，等于没有重点。

3.8 CVD 论文图测

图表在色盲读者眼里还看得懂吗？拿真实数据现场测一遍。

1 原案例

投出去一张论文图，审稿人回了句「figure 2 is hard to read」。自查排版、字号、图例，都没问题 —— 有没有可能，是因为审稿人是色觉缺陷者（CVD）？约 8% 的男性读不出靠颜色区分的那几类。先看三张最常见的「论文图」在 CVD 下的实测结果：

论文图配色方案CVD 实测结论
图 1 · 5 类别散点Wong 2011 / Okabe–Ito✅ 红盲 / 绿盲 / 蓝盲三种模拟下都能区分
图 2 · 顺序型热图Viridis / Cividis✅ 亮度单调递增，CVD 与灰度打印下仍可读
图 3 · 红 / 绿双色对比红—绿（错误案例）⚠ 绿盲眼中两者几乎同色 —— 最严重的可访问性问题

问题不在「图丑」，而在信息在部分读者眼中直接消失：图 3 的两个类别的差异，对色盲读者来说等于没有编码。

2 嵌入理论

三类 CVD 与「双编码」补救

  • 红色盲（protanopia）：约 1% 男性，红色通道感光缺失，红—绿方向坍缩。
  • 绿色盲（deuteranopia）：约 6% 男性，最常见，同样让红—绿难以区分。
  • 蓝色盲（tritanopia）：极罕见，蓝—黄方向受影响。

测试流程：① 导出原图 PNG → ② 用 Coblis / Color Oracle 模拟三类 CVD → ③ 检查是否仍能区分。判据有三条：亮度对比是否还够、形状 / 标签是否独立于颜色、类别是否还有非颜色的第二编码。

双编码（redundant encoding）是通用解法：颜色再叠一层形状（圆 / 方 / 三角 / 叉）或直接标注类别。这样即使颜色坍缩，形状仍能把类别分开 —— 灰度打印时同样受益。

3 ⭐ 关键代码
① CVD 模拟：Machado 2009 一类近似矩阵 
// 三种色觉缺陷用 3×3 线性变换近似（Machado et al. 2009 一类拟合）
const CVD_MATRICES = {
  protanopia:   [[0.567, 0.433, 0.000], [0.558, 0.442, 0.000], [0.000, 0.242, 0.758]],
  deuteranopia: [[0.625, 0.375, 0.000], [0.700, 0.300, 0.000], [0.000, 0.300, 0.700]],
  tritanopia:   [[0.950, 0.050, 0.000], [0.000, 0.433, 0.567], [0.000, 0.475, 0.525]],
};

// 对单个颜色应用矩阵，结果钳到 0-255（矩阵行 × 输入向量）
function simulateCVD([r, g, b], type) {
  const m = CVD_MATRICES[type];
  return m.map((row) =>
    Math.round(Math.max(0, Math.min(255, row[0] * r + row[1] * g + row[2] * b)))
  );
}

矩阵的每一行就是「新通道 = 原三通道的加权和」。红/绿盲矩阵里红绿两行高度相似，这正是「红绿坍缩」的数学来源 —— 绿色盲那一行 [0.625, 0.375, 0] 与 [0.700, 0.300, 0] 几乎是同一个方向。

② 就地给整张 SVG 重着色（标签不动） 
// 遍历所有填色元素，用矩阵把它们换成模拟色；文字 / 描边保持原样
function simulateSvg(svg, type) {
  svg.querySelectorAll('[fill]').forEach((el) => {
    if (!el.dataset.origFill) el.dataset.origFill = el.getAttribute('fill');   // 备份原色，切回正常时恢复
    const rgb = parseCssColor(el.dataset.origFill);                    // 兼容 hex 与 rgb()
    el.setAttribute('fill', rgbStr(simulateCVD(rgb, type)));
  });
}
// 切回「正常」：把备份的原色写回去即可
svg.querySelectorAll('[data-orig-fill]').forEach((el) => el.setAttribute('fill', el.dataset.origFill));

关键是只改 fill、不动 stroke 和文字：如果连文字也一起变换，读者根本读不出「这是模拟视图」还是「这是真的图」。此外备份原色（dataset.origFill）让「切回正常」变成一次还原，避免反复变换造成误差累积。

③ 灰度自检：亮度是否还分得开 
// WCAG 相对亮度：先 γ 解码再按 0.2126 / 0.7152 / 0.0722 加权
function luminance([r, g, b]) {
  const lin = (v) => {
    v /= 255;
    return v <= 0.03928 ? v / 12.92 : Math.pow((v + 0.055) / 1.055, 2.4);
  };
  return 0.2126 * lin(r) + 0.7152 * lin(g) + 0.0722 * lin(b);
}

// 两个类的亮度差 < 0.05 → 灰度打印后基本糊在一起，需要第二编码
const grayClash = (c1, c2) => Math.abs(luminance(c1) - luminance(c2)) < 0.05;

灰度自检是 CVD 测试的兄弟：论文常被黑白打印，如果两类颜色只在色相上不同、亮度却一样，灰度下就消失了。用同一个 luminance() 还能顺便算 WCAG 对比度（见 3.4），一举两得。

④ 原创 · CVD 复查滤镜与病例判定（配色急诊室） 
// ① 一行矩阵乘法换一双眼睛：给任意 hex 上 CVD 滤镜
function filt(hex) {
  if (mode === "normal") return hex;
  return "#" + cvdSim(hex2rgb(hex), mode)         // 与 ③ Machado 同一套矩阵
    .map(v => v.toString(16).padStart(2, "0")).join("");
}

// ② 病例判定：选对即「治愈」换安全色板，选错留下病理分析
btn.addEventListener("click", () => {
  const o = patient.options[+btn.dataset.i];
  if (o.ok) cured.add(patient.id);          // 治愈 → 用 o.colors 重上色
  else { patient.note = o.why; o._bad = true; } // 误诊 → 划线 + 病理分析
  render();
});

对应演示：配色急诊室（每病例三选一开药方）。滤镜与 3.8 的 Machado 矩阵是同一套代码 —— 病例全部治愈后切到 CVD 模式，就能复查新色板在色觉缺陷下是否仍可区分；_bad 划线让误诊成为教学素材，而不是一罚了之。

点「正常 / 红盲 / 绿盲 / 蓝盲」切换模拟模式，右侧三张真实论文图（5 类别散点、顺序型热图、红绿对比）会同时重着色；再点「颜色 + 形状双编码」看红绿对比加上形状后是否救得回来。数据来自 crime.csv 的真实州级记录。

原创演示 · 配色急诊室：4 个「配色生病」的病例，每个病例三选一开药方 —— 选对即治愈并复色，选错给病理分析；全部治愈后可用 CVD 滤镜复查。通关即复习完本章四条配色底线。

理论透视 · 配色的第一定律：数据类型决定色阶类型——顺序数据（量的大小）用单色亮度渐变，发散数据（以中点为界）用双端发散色阶，类别数据（无序集合）用类别色板（色相区分、亮度相近）。四个病例对应四种典型病：彩虹色阶的色相没有感知顺序；红绿对是色觉障碍的高危组合（约 8% 男性红绿色弱，deuteranopia 下两色几乎重合）；双线明度过近让颜色通道失效；渐变硬画无序类别会凭空暗示顺序。修复思路各有讲究：顺序靠亮度单调递进、对错改用蓝橙对、区分叠加亮度差、类别直接换 Okabe-Ito 安全色板。最后一条通用原则：重要区分永远不要只靠色相——叠加形状、标签或线型做冗余编码，才是万无一失的图。

本节小结

  • 约 8% 男性有色觉缺陷，绿色盲最常见；红—绿是最危险的配色方向。
  • CVD 测试流程：导出原图 → 模拟三类色觉缺陷 → 检查亮度 / 形状 / 标签是否仍能区分。
  • 通用补救是双编码：颜色之外再叠形状或标注，让它同时通过 CVD 与灰度打印两道关。
自测 · 1 题

一张靠红 / 绿区分两类别的图，在 CVD 测试中被发现「绿盲眼中两类几乎同色」。最有效的补救做法是？

补救要同时解决两件事：换掉会坍缩的配色（如 Wong / Okabe–Ito），并给每类加一层独立于颜色的编码（形状 / 标注）。只调亮度常不够（色相仍近），放大图例和写说明更是「知道是红绿也没用」—— 读者压根分不出哪个是红哪个是绿。

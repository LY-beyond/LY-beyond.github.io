5.1 Temporal attributes

Before drawing a time-series chart, answer one question: is the "time" I have an instant, an interval, or a cycle?

1 Original example

The original Section 6.1 listed temporal attributes in a "glossary table", yet after reading it, how to use them would still be unclear. This section puts them on a circular wheel: click an attribute and its definition, a real-life example, and its most typical visualization appear right next to it.

The wheel holds five attributes that map directly onto axes: instant, interval, span, frequency, and cycle. They are not five mutually exclusive data types, but five angles from which "the same time column" can be questioned — a phone-number table asks about instants, a heart-rate curve asks about intervals, and a monthly sales report asks about cycles.

2 Theory

Chen Wei's textbook: time is a structured dimension

The textbook stresses that time is not an ordinary numeric axis; it carries five properties of its own: order (any two events can be compared in sequence, tightly linked to causality), continuity (there is always another instant between two instants), periodicity (natural processes often cycle — day and night, seasons — expressible as a cyclic time domain), independence from space (time and space are closely related, yet most scientific processes treat them separately), and structure (hierarchical splits of year / month / day / hour / minute / second, covering both the natural day-night cycle and man-made conventions such as 60 seconds).

  • Treat an "instant" as a point → scatter plots, event markers; treat an "interval" as a length → Gantt charts, timeline brackets.
  • Treat a "span" as a range → area charts, time-axis range highlighting.
  • Ignore periodicity → seasonal trends get "flattened" by a linear time axis, leaving only a jagged line with no visible pattern.

Thinking these five attributes through blocks four common mistakes: missing order (a scatter plot turns into misaligned noise), confused continuity (discrete events forcibly joined into a line), ignored periodicity (seasonal trends flattened), and mismatched structure (weekdays / weekends and leap years all miscounted).

② Layout of the circular wheel: angle → polar → Cartesian 
// ⭐ Five nodes split 360°: start straight up (-90°), one step every 72°
const N = 5;
const nodeAt = (i) => {
  const deg = -90 + i * (360 / N);
  const rad = deg * Math.PI / 180;
  return {
    x: CX + R * Math.cos(rad),   // polar = (R, θ)
    y: CY + R * Math.sin(rad),   // to Cartesian = (x, y)
    rad,
  };
};
// Adjacent points are always 72° apart, so the node spacing is naturally even

The general recipe for polar layouts: first fix the angle (θ = start + i·360/N), then multiply by the radius to get x / y. Earlier chapters drew pyramids with M / L / Z line commands; here they become cos / sin — polar coordinates are the universal entry point for "circular graphics" (wheels, radar charts, spirals, pie charts).

  • Time can be questioned from five angles: instant (a point), interval (a length), span (a range), frequency (a repeat count), and cycle (a loop).

Self-test · Q1

The data point "the temperature reading at 08:00 on March 1, 2024" belongs to which temporal attribute?

It lands on a single instant and is a point, so it is an instant. An interval needs two instants subtracted (e.g. "from 08:00 to 12:00 is 4 hours"); a span is a whole continuously covered range; a cycle is a repeating segment that returns to its start — none of the three is a property of this single data point.

Self-test · Q2

When designing a time-series chart, ignoring periodicity is most likely to cause?

A linear time axis lays every year or day out side by side, stretching a periodic signal into a jagged line with no visible pattern; this is exactly why one switches from a line chart to a calendar heatmap (5.3) or a spiral (5.4). Option a corresponds to "missing order", b to "confused continuity", and d to "mismatched structure".

5.2 Standard time visualization (line charts)

x axis = time, y axis = measure. The most common time-series chart — and the one whose conclusions are most easily swayed by "aggregation scale".

1 Original example

The original Section 6.2.1 used a line chart to show how the usage frequency of French names (Marie / Jean / Camille) changed from 1900 to 2020. The original page also had a "word cloud + hover highlight + time-range filter", but the code only showed the few key lines of the line chart.

Weekly aggregationabout 53Week-level ups and downs, short-term trendThe specific day within a week

2 Theory

A standard time-series chart = a 2D line chart

At heart it is a 2D line chart with "x = time, y = measure"; its strength is that trends over a linear time domain are immediately clear, and its cost is that periodicity is hard to express — which is exactly why the calendar heatmap in 5.3 and the spiral in 5.4 exist. Interactively, hover highlight, tooltips, and time-range filtering are already standard in data journalism.

  • Choosing a curve: with ≤ 50 points use linear (faithful to the data); with 50–500 use monotoneX / curveCatmullRom (smooth but no overshoot); only above 500 consider an area or box plot.
  • The aggregation trade-off: aggregation reduces noise and makes trends clearer, but every step of aggregation is "trading detail for clarity", so conclusions may change because of it.

The rule of thumb is to pick the scale after the goal: to answer "did it rain on a given day" use daily data; to answer "was this summer hot" use monthly aggregation; to answer both, place them side by side (which is exactly what this section's demo does).

3 ⭐ Key code
① Time string → Date, then hand it to the time axis 
// ⭐ The year in the CSV is the string '1965'; parse it into a Date first
const parseYear = d3.timeParse('%Y');      // '1965' → Date
const formatYear = d3.timeFormat('%Y');     // Date → '1965'
// Common tokens: %Y four-digit year · %m month 01-12 · %d day · %H hour · %M minute

// A time axis is a specialized numeric axis (a Date is a number underneath)
const x = d3.scaleTime()
  .domain([new Date(1900, 0, 1), new Date(2020, 11, 31)])
  .range([0, innerW]);

svg.append('g')
  .attr('transform', `translate(${M.l},${M.t + innerH})`)
  .call(d3.axisBottom(x).ticks(10));

parseYear handles string → Date, the first step for any time-series data (CSV files almost never contain a real date type). scaleTime adds two capabilities over scaleLinear: ① it automatically picks the tick interval by time span (10 years / 12 months / 30 days); ② timezone handling (in real projects remember to add .utc()).

② Aggregation: rolling a daily series up into weekly / monthly means 
// ⭐ Group by "belonging week / month", then average — one piece of code, three scales
const byWeek = d3.rollup(
  daily,
  (v) => d3.mean(v, (d) => d.temp),         // reducer: mean
  (d) => d3.timeWeek.floor(d.date)           // key: this day's "week start"
);
const byMonth = d3.rollup(
  daily,
  (v) => d3.mean(v, (d) => d.temp),
  (d) => d3.timeMonth.floor(d.date)          // key: this day's "month start"
);
// rollup returns Map(Date → mean); spread it with [ ...map ] to plot

The key lies in the key-extraction function: timeWeek.floor(date) folds "any day of this week" back to the same week start, so points in the same week naturally form one group. The rollup (grouped aggregation) learned in Chapter 1 finally earns its keep here — switching aggregation scale is essentially just switching the key function.

③ A generic hover template: transparent overlay + focus group 
// ⭐ Three layers: transparent rect captures events / focus group shows / text shows the value
const focus = svg.append('g').style('display', 'none');
focus.append('line').attr('class', 'hover-line');   // vertical guide line
focus.append('circle').attr('r', 4);                // dot
focus.append('text').attr('class', 'tip');              // value

svg.append('rect')                                  // overlay
  .attr('width', innerW).attr('height', innerH)
  .attr('fill', 'none').attr('pointer-events', 'all')
  .on('mousemove', (event) => {
    const [mx] = d3.pointer(event);
    const date = x.invert(mx - M.l);              // pixel → data
    const i = d3.bisector((d) => d.date).left(series, date);  // find nearest point
    focus.attr('transform', `translate(${x(series[i].date)},0)`);
  });

Remember this trio (transparent rect + focus group + bisector) — it applies to almost every time-series chart. x.invert() converts mouse pixels back into data values, and d3.bisector uses binary search to find the nearest point — faster and more accurate than a hand-written loop.

The larger k or the smaller α, the more the noise readout drops — and the more the peak lags — the granularity–noise–lag triangle made directly visible in two numbers. Original demo · Smoothing Lab: one real time series (French names) — tune the window k and switch between moving average / median / EWMA live, and read out "how many years the peak lags, how much noise drops" — feel the granularity–noise–lag trade-off hands-on.

Theory lens · Smoothing is low-pass filtering: the mathematical essence of smoothing is to keep the low-frequency trend and suppress high-frequency noise, and the three smoothers are three routes to the same goal — the moving average applies an equal-weight window (larger k → smoother, lag ≈ (k−1)/2 years); the median filter replaces the center value with an order statistic, nearly immune to outliers at the cost of a staircase look; EWMA recurses st = α·yt + (1−α)·st−1, weighting exponentially and storing a single number (O(1) memory), with lag ≈ (1−α)/α years. All three face the granularity–noise–lag trade-off: a wider window cuts noise but flattens and delays peaks — there is no perfect parameter, only a choice that matches the question. And one rule of ethics: a smoothed line is a model, not the data — always show the raw line next to it, exactly as this demo does.

Section summary

  • A standard time-series chart is a 2D line chart with "x = time, y = measure"; it excels at trend, not at periodicity.
  • Aggregation scale (raw / weekly / monthly) markedly changes shape and conclusions — switching scale is essentially just switching the rollup key function.
  • Choose curve smoothness by point count: ≤ 50 use linear, 50–500 use monotoneX / Catmull-Rom, above 500 consider an area chart.
Self-test · Q1

After aggregating a 366-day temperature series by week and then drawing a line, the most direct effect is?

Aggregation is "trading detail for clarity": 366 points are folded into about 53, noise is averaged away and the trend becomes more obvious, at the cost of no longer seeing the differences between individual days of a week. It does not turn the time domain into a cyclic one — that is what the spiral in 5.4 does.

Self-test · Q2

Compared with d3.scaleLinear, what extra core capability does d3.scaleTime add?

scaleTime adds a "time semantics" layer on top of the numeric axis: it automatically picks the tick interval by span (ten years / twelve months / thirty days) and provides .utc() for timezones. Turning strings into Dates relies on timeParse, aggregation relies on rollup, and drawing smooth curves relies on curve* — none of which is the scale's job.

5.3 Calendar heatmap (van Wijk)

Spread "a whole year" into a grid: x = week, y = weekday, color = value — seasonality surfaces at a glance.

1 Original example

The original Section 6.2.2 used a calendar heatmap to show Beijing's daily maximum temperature in 2024, with a red line separating each month. This section reuses the same data (data/weather_2024.csv, 366 days) and fully explains "why this layout is easier to read than a line chart".

A line chart answers "how it changes over time"; a calendar heatmap answers "how it changes with season / weekday". The same 366 days of data become 366 peaks and troughs in a line chart, yet a calendar shows at a glance: winter is all blue, summer is all red, plus a column rhythm repeating every 7 days.

2 Theory

van Wijk 2008: the coordinate convention of a calendar heatmap

The calendar heatmap was proposed by van Wijk in 2008: x = week (which week of the year), y = weekday, color = value. It suits three kinds of tasks especially well: ① long series (spanning years) + ② periodicity (weekday / month) + ③ anomaly detection (holidays, weekdays vs weekends).

  • Which day starts the week: starting each week on Sunday or Monday directly changes where "the weekend" sits visually — Chinese-language contexts often switch to a Monday start.
  • Month separation: cutting the months apart with red lines is far easier to read than a bare 7 × 53 grid.
  • Color scheme: use a sequential colormap (e.g. Viridis), because "temperature high/low" is ordered — see Section 3.2 on colormaps in Chapter 3.

The elegance of isMonthDivider: there is no need to loop "to find the first day of each month" — just check whether "today and 7 days ago are in the same month": same month means no line, different month means drawing a divider. A single O(n) pass suffices, and it is naturally correct.

3 ⭐ Key code
① d3.timeDay.range splits "a year" into "one day at a time" 
// ⭐ Split a whole year by day; leap year 366 / common year 365 handled automatically
const days = d3.timeDay.range(
  new Date(2024, 0, 1),      // 2024-01-01
  new Date(2025, 0, 1)       // 2025-01-01
).map((d) => ({
  date: d,
  value: byKey.get(d3.timeFormat('%Y-%m-%d')(d)) ?? 0,
}));
console.log(days.length);   // 366 (2024 is a leap year)

d3.timeDay.range(start, stop) hits "continuity + structure" in one move: it lays out days at daily granularity continuously, and automatically handles months and leap years. A small pitfall: timeFormat('%Y-%m-%d') must match the date string keys in the CSV exactly, otherwise whole days fail to line up and holes appear in the heatmap.

② Week-column / weekday-row layout with Sunday as the start 
// ⭐ Column = which week of the year this is (days divided by 7); row = weekday
function weekCol(date) {
  return Math.floor(d3.timeDay.count(d3.timeYear.floor(date), date) / 7);
}
function dayRow(date) {
  return date.getDay();     // 0=Sun, 1=Mon, … 6=Sat
}

g.selectAll('rect.cell')
  .data(days).join('rect')
  .attr('x', (d) => weekCol(d.date) * cellSize)
  .attr('y', (d) => dayRow(d.date) * cellSize)
  .attr('width', cellSize).attr('height', cellSize)
  .attr('fill', (d) => color(d.value));

Sunday vs Monday is the design fork of a calendar heatmap: getDay() uses Sunday as 0, the English-calendar tradition; Chinese-language contexts often change the row order to (getDay() + 6) % 7 so Monday sits in the first row. This round's demo offers a "Sunday start / Monday start" switch; toggling it shows "the weekend" changing position in the grid.

③ isMonthDivider: a single pass for month-divider lines 
// ⭐ Check whether "today and 7 days ago are in the same month": no line if same, line if different
function isMonthDivider(date) {
  const sevenDaysAgo = d3.timeDay.offset(date, -7);
  return date.getFullYear() !== sevenDaysAgo.getFullYear()
      || date.getMonth()    !== sevenDaysAgo.getMonth();
}

// Draw a vertical line: cut the month-crossing column from top to bottom
g.selectAll('line.mdiv')
  .data(days.filter((d) => isMonthDivider(d.date))).join('line')
  .attr('x1', (d) => weekCol(d.date) * cellSize)
  .attr('x2', (d) => weekCol(d.date) * cellSize)
  .attr('y1', (d) => dayRow(d.date) * cellSize)
  .attr('y2', (d) => dayRow(d.date) * cellSize + cellSize);

With the intuitive "find the first day of each month" approach, 28 / 29 / 30 / 31-day differences would all need handling, and "column crossings" are easily missed. The "look back 7 days" approach uses only a single O(n) pass, naturally covering every month length and leap years — this is the ingenuity of van Wijk's algorithm.

Section summary

  • A calendar heatmap = week columns × weekday rows × color encoding, proposed by van Wijk in 2008, purpose-built for "long series + periodicity + anomaly detection".
  • Month separation is judged by "whether 7 days ago is in the same month"; a single O(n) pass suffices, without finding each month's first day.

Self-test · 1 question

isMonthDivider(date) uses "whether 7 days ago is in the same month" to decide whether to draw a month divider. What is the benefit of writing it this way?

Handing "is this a month crossing" to a comparison of two adjacent weeks sidesteps the question of "how many days each month has": regardless of 28 / 29 / 30 / 31 days, only a 7-day look-ahead is needed, completing it in one traversal. It neither computes temperatures nor decides colors — that is the job of the reducer and the colormap.

5.4 Cyclic time visualization (Archimedean spiral)

A line expresses trend, a circle expresses cycle; a spiral = a circle + continuous unwinding — coil a year into a spiral and periodicity is visible at a glance.

1 Original example

The original Section 6.2.3 used an Archimedean spiral (constant-speed spiral) to lay out dates: each loop represents 1 year / 1 month / 1 week, and each date maps to one ring segment on the spiral. This section continues with the 2024 daily temperatures and offers a three-way switch for "each loop = 1 year / 1 season / 1 month" — the same data, wound into different numbers of loops, reveals different levels of cycles.

Each loop representsLoops (one year, 2024)Visible cycles
1 year1 loopA single seasonal cycle across the year
1 season4 loopsThe advance and retreat of the four seasons
1 monthabout 12 loopsShort cycles fluctuating within and between months
2 Theory

Spiral vs line: two time domains

A line lays time out on a linear time domain and excels at expressing "trend"; a spiral lays time out on a cyclic time domain, repeating around a circle, and excels at expressing "cycles". The formula of the Archimedean spiral is r = a + bθ: constant-speed unwinding, the radius increasing by a constant b on every turn — if b = 0, it degenerates into an ordinary circle.

  • The dynamic-Δθ algorithm: the elegant point of the original document, Δθ = boxSize / √(b² + r²), keeps each ring segment's arc length approximately equal, so the visual stays consistent even as the radius keeps growing.
  • The practical trade-off: a spiral suits cycles with clear repetition such as "year / season / week", but is unsuited to data with "no cycle" or "too long a cycle".

A spiral brings "adjacent loops" visually very close, so readers easily misread them as "happening at the same time". Always mark the start of each loop (this demo uses month labels) and let readers know "how long one loop is".

3 ⭐ Key code
① Polar → Cartesian: r = a + bθ 
// ⭐ Ring width and gap between coils
const boxSize = 22;
const coilGap = boxSize * 1.4;            // radial gap between adjacent coils
const b = coilGap / (2 * Math.PI);          // constant r gains per full turn
const startRadius = 60;
let theta = (startRadius - 0) / b;         // starting angle

function pos(t) {                       // t: angle (radians)
  const r = 0 + b * t;                    // Archimedean spiral: r is proportional to θ
  return { x: r * Math.cos(t), y: r * Math.sin(t), r };
}

Polar is (r, θ) and Cartesian is (x, y): every 2π added to θ adds b to r, which is exactly "expanding one notch outward per turn". The larger b is, the looser the coils and the more "unfurled" the spiral; when b = 0 it degenerates fully into a circle — which also shows that "a circle" is a special case of a spiral.

② A dynamic angle increment: making every arc length approximately equal 
// ⭐ Arc length = r · Δθ. The larger r is, the longer the arc for the same Δθ
function angleDelta(currentR) {
  return boxSize / Math.sqrt(b * b + currentR * currentR);
}
// Equivalent to "arc length ≈ boxSize": every cell looks the same size

let t = theta;
for (let day = 0; day < dayCount; day++) {
  const p = pos(t);
  // … draw the ring segment for day (t → t + Δθ)
  t += angleDelta(p.r);          // the angle increment shrinks dynamically with radius
}

This is the core insight of the original document: the outer radius is large, so if the angle increment is constant, cells get "stretched". Writing Δθ as integer width / √(b² + r²) is equivalent to making every cell's arc length roughly equal to boxSize, so inner and outer coils look equally tidy. The cost: one loop no longer equals exactly 2π, so "each loop = one cycle" must be read by loop index rather than by angle.

③ The ring-segment path: M / L / Z across a cell's four vertices 
// ⭐ Four key points: start-outer → end-outer → end-inner → start-inner, closing back to start
function segmentPath(t0, t1, r0, r1, halfWidth) {
  const at = (t, rr) => [rr * Math.cos(t), rr * Math.sin(t)];
  const [x0o, y0o] = at(t0, r0 + halfWidth);     // start · outer
  const [x1o, y1o] = at(t1, r1 + halfWidth);     // end · outer
  const [x1i, y1i] = at(t1, r1 - halfWidth);     // end · inner
  const [x0i, y0i] = at(t0, r0 - halfWidth);     // start · inner
  return `M ${x0o} ${y0o} L ${x1o} ${y1o} L ${x1i} ${y1i} L ${x0i} ${y0i} Z`;
}

A ring segment is just an M / L / L / L / Z path — exactly the same line commands learned in 5.1. Why not use d3.arc(): it computes by "arc angle" and cannot be applied directly to a spiral whose radius keeps changing; hand-computing the four vertices is more flexible instead.

Section summary

  • A spiral places time in a "cyclic time domain": r = a + bθ, the radius gains a constant b each turn, and b = 0 degenerates into a circle.
  • A dynamic Δθ = boxSize / √(b² + r²) keeps each arc length approximately equal, fixing the visual inconsistency of "outer cells being stretched".
  • Each date = one ring segment, whose path is the four vertices of M / L / L / L / Z — no need to rely on d3.arc().
Self-test · 1 question

Why use a dynamic angle increment Δθ = boxSize / √(b² + r²) instead of a fixed Δθ?

Arc length ≈ r · Δθ, so the larger the radius r, the longer the arc. Making Δθ decrease as r grows keeps every cell's arc length near boxSize, so inner and outer coils look consistent. The cost is that "one loop" no longer equals exactly 2π — so cycles must be read via the loop index, not the angle.

5.5 Storyline timeline (Jurassic Park)

Multiple "lifelines" laid side by side on a time axis: lines converging = encounter / conflict, lines diverging = separation — turning a narrative into a chart.

1 Original example

The original Section 6.2.4 built a Storyline timeline from Jurassic Park's five characters (Alan & Kids / T-REX / Raptors / Malcolm / Dilophosaurus), with the event layer marking key conflicts as translucent red circles. This section reuses that narrative data (rewritten as an inline constant inside lesson.js) and adds "click a line to read its appearance interval and key nodes".

2 Theory

Ogawa & Ma 2008: breaking a narrative into lifelines

Storyline was proposed by Ogawa & Ma at Stanford University in 2008, originally for films and academic-collaborator networks. At its core is abstracting each character / organization / process into a lifeline: lines converging = a character encounter or conflict, lines diverging = characters separating — so "who is with whom, and when" becomes readable geometry.

  1. Time-scale mapping: movie duration → SVG width, with the x axis aligned strictly proportionally (0–127 min).
  2. Spline smoothing: Catmull-Rom curves with a tension of 0.5 — "flowing naturally" but not "over-bending".
  3. Event layer: translucent red circles + text marking key turning points, decoupled from the line layer.

Why Catmull-Rom rather than monotoneX? monotoneX guarantees "no over-bending", but it draws lines too straight and loses the narrative's "river feel". Catmull-Rom's tension of 0.5 is an empirical value: softer than 0 (that sense of story) and steadier than 1.0 (no oscillation). Only when fitting scientific curves is the tension dropped to 0.2–0.3.

3 ⭐ Key code
① Each character = one path (time-scale mapping) 
// ⭐ X axis: 0–127 min → screen width; each line uses y to express "relationship"
const x = d3.scaleLinear().domain([0, 127]).range([M.l, W - M.r]);

const characters = [
  { name: 'Alan & Kids', token: '--ch-1', points: [
    { time: 5,  y: 80 }, { time: 18, y: 130 },
    { time: 78, y: 80 }, { time: 125, y: 40 },
  ]},
  { name: 'T-REX',       token: '--c-danger', points: [
    { time: 75, y: 280 }, { time: 78, y: 130 },
    { time: 120, y: 290 },
  ]},
];

const line = d3.line()
  .x((d) => x(d.time))
  .y((d) => yScale(d.y))
  .curve(d3.curveCatmullRom.alpha(0.5));   // tension 0.5

characters.forEach((c) => {
  svg.append('path').datum(c.points)
    .attr('d', line)
    .attr('stroke', getToken(c.token))
    .attr('stroke-width', 3)
    .attr('fill', 'none');
});

Using the y value to express "relationship" is the key: both T-REX and Alan draw their lines to y = 130 (at the same instant t = 78), so the two lines converge visually — expressing "T-REX attacked Alan at minute 78". This is not algorithmically generated but hand-crafted narrative design; the library only provides the tool for "adjusting y by hand".

② Event layer: narrative anchors decoupled from the line layer 
// ⭐ The event layer is a separate <g>: translucent red circle + dot + text
const events = [
  { time: 78, y: 105, name: 'T-REX Attack',
    desc: 'T-REX breaks out of its pen and attacks Alan & the kids\' car' },
  { time: 48, y: 335, name: 'Nedry Incident',
    desc: 'Dilophosaurus attacks Nedry amid the blackout' },
];

const layer = svg.append('g').attr('class', 'event-layer');
events.forEach((ev) => {                       // read-only render; events don't modify the lines
  const g = layer.append('g').attr('tabindex', 0);   // focusable, so keyboard users can see it too
  g.append('circle').attr('cx', x(ev.time)).attr('cy', yScale(ev.y))
    .attr('r', 18).attr('fill', 'color-mix(in srgb, var(--c-danger) 18%, transparent)');
  g.append('text').attr('x', x(ev.time)).attr('y', yScale(ev.y) - 9)
    .attr('text-anchor', 'middle').text(ev.name);
});

The value of the two-layer structure: the line layer handles "the flow of relationships", the event layer handles "the anchors of the narrative". Once decoupled, the two can animate independently and be filtered independently without interfering with each other — which is also why Storyline can be extended into "multi-person case timelines" and "project task handovers".

③ alpha(0.5): how to choose the tension coefficient 
// curveCatmullRom.alpha(t), t ranges 0 → 1
d3.line().curve(d3.curveCatmullRom.alpha(0.0));  // close to a straight line (the "hardest")
d3.line().curve(d3.curveCatmullRom.alpha(0.5));  // standard Catmull-Rom (recommended)
d3.line().curve(d3.curveCatmullRom.alpha(1.0));  // highly curved (prone to oscillation)

// d3-free equivalent approximation: interpolate control points between "line ↔ Catmull-Rom"
// the two control points for the curve segment p1→p2:
//   line version  c1 = p1 + (p2 - p1)/3,  c2 = p2 - (p2 - p1)/3
//   Catmull version c1 = p1 + (p2 - p0)/6,  c2 = p2 - (p3 - p1)/6
// c = lerp(line version, Catmull version, t)  → cubic Bézier approximation

0.5 is an empirical value: softer than 0 (it looks like it has a sense of story) and steadier than 1.0 (no roller coaster). Use 0.5 for time-based narratives; use 0.2–0.3 for scientific curve fitting so the line hugs the data. This page's demo approximates Catmull-Rom with "piecewise cubic Bézier" (no d3 pulled in) and adjusts tension with a slider, matching the effect of alpha.

Section summary

  • Storyline abstracts characters / organizations / processes into lifelines: converging = encounter / conflict, diverging = separation.
  • All three elements are essential: time-scale mapping, the Catmull-Rom spline, and an event layer decoupled from the line layer.
  • A tension of 0.5 is the rule of thumb for narrative; to stay faithful to data, lower the tension to 0.2–0.3 or just use monotoneX.
Self-test · 1 question

In a Storyline timeline, what does a lifeline's y-axis position express?

Storyline's y axis is not a numeric axis but a relationship axis: two lines drawn to the same height tell the reader "these two characters are together, or in conflict, right now". Only the x axis is time (mapped strictly proportionally); appearance order and numeric size are both expressed by x.

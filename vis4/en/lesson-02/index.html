2.1 The Visualization Pipeline (Card · Mackinlay · van Wijk)

Three classic models describe three faces of the same thing: a pipeline, an automatic decision procedure, and a feedback loop.

1 Original case

This chapter only ever uses one dataset: the China University of Petroleum (East China) 2025 freshman roster newstudent.csv, with 80 records and 8 columns (No. / Name / Gender / Birthday / Age / Class / Hometown / Ethnicity).

The original site's 2.1 gave a concept diagram of "3 visualization pipeline models". In this lesson we redraw it as an interactive data-flow pipeline diagram: click any stage to see what it corresponds to in each of the three models.

Three models: three faces of the same thing
ModelAuthor / YearQuestion it answers
Card data-flow modelCard, Mackinlay & Shneiderman, 1999"What comes first, what comes next" — gives the pipeline its order
Mackinlay automation principlesMackinlay, 1986"How the mapping step decides automatically" — which channel to pick
van Wijk feedback modelvan Wijk, 2005"How to feed user actions back after the view" — the feedback loop
2 Embedded theory

Card data-flow model (1999): the "pipeline" of visualization

Splits visualization into four stages: Raw Data → Data Tables → Visual Structure → Views. Between stages are nested transformations D → T → V → C/L/S: data transformation (D→T), visual mapping (T→V), view transformation (V→C/L/S, i.e. Camera / Light / Screen).

Mackinlay automation principles (1986): how mapping decides automatically

For each data type, automatically pick the visual channel with the smallest quantization error: numeric → position (most accurate), ordinal → length / density, categorical → hue / shape. It addresses the "data tables → visual structure" step of the pipeline.

van Wijk feedback model (2005): drawing interaction as a loop

The classic pipeline is one-directional; van Wijk emphasizes the interactive feedback loop: View ⇆ Filter ⇆ Param ⇆ Other Views. The user reads the view → changes the filter / parameters → triggers a new view; view and user form a closed loop instead of a one-shot render.

Core teaching point: the three models stack rather than conflict. Card states "after transform comes mapping, after mapping comes view"; Mackinlay states "how the mapping step decides automatically"; van Wijk states "after view, user actions are still fed back".

3 ⭐ Key code
① SVG arrows: <marker> + marker-end 
// 1. Define the arrow shape inside <defs> and name it with an id
svg.append("defs").append("marker")
   .attr("id", "arrowhead")
   .attr("viewBox", "0 -5 10 10")
   .attr("refX", 8)            // Align the arrow tip so it touches the node edge
   .attr("orient", "auto")      // Rotate automatically to follow the line direction
   .append("path").attr("d", "M0,-5L10,0L0,5");

// 2. Attach the arrow to the end of the line with marker-end="url(#arrowhead)"
svg.append("line")
   .attr("marker-end", "url(#arrowhead)")
   .attr("x1", x1).attr("y1", y).attr("x2", x2).attr("y2", y);

marker-end="url(#arrowhead)" is SVG's reference mechanism — a URL reuses a shape defined in <defs> at the end of a line. refX sets the arrow tip's offset relative to the line's endpoint, and orient="auto" makes the arrow rotate automatically. A single marker can serve all lines; no separate triangle is needed for each arrow.

② classed: toggling the state of all nodes at once 
// Single-select: refresh the selected state of every node at once
svg.selectAll(".node")
   .classed("selected", n => n.id === d.id);   // takes a boolean function

classed(name, predicate) takes a boolean function and toggles the class of every node at once, far more concise than a hand-written forEach + classList.toggle. It only changes the class; the actual appearance (highlight, stroke) is left to CSS — a textbook example of D3 separating "state" from "style".

③ Data-driven pipeline: binding the stage array to SVG nodes 
const STAGES = ["Raw Data", "Data Tables", "Visual Structure", "Views"];

svg.selectAll(".stage").data(STAGES).join("g")
   .attr("class", "stage")
   .attr("transform", (d, i) => `translate(${i * 160}, 0)`);

Each pipeline stage is one binding of "data → mark". Swap STAGES for another array and the whole diagram changes — this is D3's core idea: the document is driven by data. The tree, the list, and the aggregate charts later in this chapter all use the same join pattern.

④ Original · A spec-driven mini renderer (Graphical-spec Generator) 
// ① Data transform: group by the X channel → aggregate by the Y channel (hand-rolled rollup)

  : grp.reduce((s, d) => s + d.age, 0) / grp.length; // mean(age)

Theory lens · Grammar of Graphics: a chart is not drawn stroke by stroke — it is described by a specification: data + statistical transformation + mark + channel mapping (encoding) + scales, all five parts indispensable. Wilkinson formalized the idea in 1999, and Vega-Lite distilled it into "the encoding is the chart": declare what x binds, how y aggregates, where color goes — and the axes, legends and grouped offsets are all derived by the renderer. In this demo, changing one dropdown = changing one line of the spec, and the whole chart redraws — the exact divide between declarative and imperative: imperative code moves coordinates, declarative code edits the description. One dataset, a different channel binding, a completely different chart — chart choice becomes a reasoned decision instead of an inspiration.

Section summary

  • Card 1999 splits visualization into a four-stage pipeline: raw data → data tables → visual structure → views, with nested transformations D→T→V→C/L/S between stages.
  • Mackinlay 1986 handles the automatic decision in the "mapping" step (numeric→position, categorical→hue); van Wijk 2005 adds the "view ⇆ user" feedback loop.
  • The three models stack: pipeline, automatic decisions, and feedback loop each cover one part; together they form the complete visualization process.
Self-test · 1 question

In the Card data-flow model, "choosing the most suitable visual channel (position) for the age attribute" belongs to which arrow?

"Mapping an attribute to a channel" is exactly visual mapping (data tables → visual structure), and it's also where the Mackinlay automation principles apply. Data transformation (D) only tidies the table; view rendering (V) only draws the already-decided marks onto the screen.

2.2 Data Transformation: Raw Data → Data Tables

Upgrading "group by class" to "group by a combination of dimensions" — this is the pipeline's first arrow, and visualization's "first mile".

1 Original case

Following the pipeline from the previous section, this section's 2.2 deals with exactly the first arrow, "raw data → data tables", i.e. data transformation.

The original case uses the freshman data to do rollup bucket aggregation by "class / major", centered on chaining calls to d3.rollup — one function completes multi-dimensional grouping. This lesson turns it into a step-by-step folding animation: 80 detail rows → group and count by class → nested aggregation by gender.

2 Embedded theory

The four data-transformation operations (Card 1999 · D layer)

Going from "raw data" to "data tables", the D layer performs four kinds of operations. The original 2.2 only covered "bucket aggregation"; here it is placed in the full framework — aggregation turns out to be just one row.

OperationWhat it doesD3 implementation
Clean / FilterDrop missing values and outliers, keep rows that meet a condition.filter(), the d3.csv(url, row) callback
Aggregate / SummarizeGroup by key and reduce each group to one valued3.rollup(), d3.group()
Join / RelateCombine two tables by key (join the student table with the class table)d3.map + a manual index
Derive / ProduceCompute a new column from an existing one (cut the "major" out of "class")compute a new field in the row callback

The rollup aggregation demoed in this section is the "aggregate" row. Once this table is understood, data transformation shows itself as the whole pipeline's "first mile" — if the data table isn't tidy, the mapping and rendering that follow are wasted.

d3.rollup = a functional composition of "bucket by key, then reduce once"

d3.rollup(data, reducer, ...keys) returns a Map (not an array, not a plain object), so iterate it with for ([k, v] of m) or m.entries(); a nested rollup yields a nested Map.
The difference from d3.group in one sentence: rollup reduces each group to a single value, while group keeps the original array.

OLAP slice / dice / drill (Codd 1993)

OLAP operationWhat it maps to
SliceFix one dimension (only the class of 2025) → .filter() then rollup
DiceGroup by two dimensions → two-key rollup
DrillDrill down level by level → nested rollup + recursive expansion

The "drill-down interaction" in visualization systems is usually just a combination of rollup + hierarchy behind the scenes.

3 ⭐ Key code
① Two-level rollup: returning a nested Map 
// outer key = class, inner key = gender, reducer = count
const nested = d3.rollup(
  students,
  v => v.length,          // reduce each group to one value (count the people)
  d => d.class,           // outer key
  d => d.gender           // inner key (a rest parameter; more can be added)
);

// iterate the nested Map:
for (const [cls, inner] of nested) {
  for (const [gender, count] of inner) {
    console.log(cls, gender, count);   // 软件工程1班 男 12
  }
}

d3.rollup's key arguments are a rest parameter (...keys): pass 1 → a single-level Map, pass 2 → a nested Map, pass 3 → three-level nesting. It returns a Map, so iterate with for...of or .entries(), not Object.keys.

② Cutting "major" out of "class" with a regex 
const data = await d3.csv("./data/newstudent.csv", d => {
  const cls = d["班级"].trim();
  const m = cls.match(/^(.+?)(\d+班)$/);  // non-greedy middle + trailing "number + 班"
  return {
    id:     +d["序号"],
    name:   d["姓名"].trim(),
    class:  cls,
    gender: d["性别"].trim(),
    major:  m ? m[1] : cls,   // 软件工程1班 → 软件工程
  };
});

In the regex, .+? is non-greedy: it keeps the middle as short as possible so that \d+班 is left for the end. Written greedily as .+, it would swallow the whole string and m[1] would be undefined. This regex pitfall trips up students constantly, so it must be mastered.

③ The one-sentence difference between group and rollup 
// group: grouping that KEEPS — each key holds the full array of elements
const byClass = d3.group(students, d => d.class);

// rollup: grouping that AGGREGATES — each key holds a single reduced value
const countByClass = d3.rollup(students, v => v.length, d => d.class);

Remember it in one line: group keeps the group, rollup aggregates the group. If both "the count" and "the roster" are needed (to drill down later), use group; if only the summary numbers are needed, rollup is more compact. The folding animation demoed in this section uses rollup for both levels.

Section summary

  • Data transformation is the pipeline's "first mile", covering four kinds of operations — clean / aggregate / join / derive — and rollup is just the "aggregate" one.
  • d3.rollup(data, reducer, ...keys) returns a Map (or a nested Map when nested); keys is a rest parameter — one more key means one more grouping level.
  • group keeps each group's original array, rollup keeps only the reduced value; the non-greedy .+? in the regex /^(.+?)(\d+班)$/ is the key to cutting out the "major".
Self-test · Q1

What does d3.rollup(students, v => v.length, d => d.class) return?

rollup returns a Map; because a reducer v => v.length was given, each group keeps only one reduced value (the count), so it does not keep the original array (that would be group's behavior).

Self-test · Q2

If the .+? in the regex /^(.+?)(\d+班)$/ is changed to a greedy .+, what happens to "数据科学2班"?

A greedy .+ first swallows as many characters as possible, leaving almost nothing for \d+班, so the first capture group can't get the major. The non-greedy .+? makes it eat as little as possible, saving "number + 班" for the end — that's the key to splitting correctly.

2.3 Visual Mapping: Data Tables → Visual Structure

Once we have hierarchical data, how do we place the nodes on screen without collisions? — the Reingold–Tilford algorithm, essentially a visual mapping along the "position" channel.

1 Original case

Following the previous section, we now have "data tables". This section's 2.3 is the second arrow, "data tables → visual structure", i.e. visual mapping. It answers one core question: which visual channel should express each attribute in the data?

The original case mentioned "tree-structure visualization". This lesson unfolds the tree-layout algorithm — group by "class / gender" to get a hierarchical tree, then place it firmly on screen.

2 Embedded theory

Visual channels and the Mackinlay ranking (1986)

Visual channels are the carriers that "encode data onto visual elements": position, length, area, angle, color, shape, texture… Mackinlay 1986 gives the classic ranking: for different data types, each channel's quantization accuracy differs.

Data typeChannel accuracy ranking (high → low)
QuantitativePosition → Length → Angle → Slope → Area
OrdinalPosition → Density → Saturation → Luminance → Volume
NominalPosition → Hue → Texture → Connection → Shape

Position always ranks first — it's most accurate for all three data types; the human eye is most sensitive to position.

Two kinds of channels: magnitude vs identity

By "whether it can express how much", channels fall into two kinds: magnitude channels express ordinal / quantitative attributes (a shared-scale position is most accurate, then length / tilt / area, and luminance / saturation / volume are weakest); identity channels express categorical attributes (spatial region, hue, motion, shape — they distinguish "which class" but not "how much"). Picking the wrong kind misleads the reader.

The Reingold–Tilford algorithm: the core of tree layout (1981)

Still the implementation core of d3.tree(), its idea is three passes:

  1. First pass (bottom-up): for each parent, measure how much horizontal space its left and right subtrees occupy.
  2. Second pass (top-down): assign each node an absolute x coordinate (keeping siblings snug to the parent's center line and non-overlapping).
  3. Third pass: handle "threads" — fix the alignment when a child crosses its parent's center line.

Complexity is O(n). All the algorithm does is "encode the hierarchy into a parent-above-child tree via the position channel" — so tree layout is essentially a visual mapping.

The d3-hierarchy toolkit

APIPurpose
hierarchy(data)Convert nested data into a hierarchy (adds parent / children / depth)
tree().size([h, w])The Reingold–Tilford algorithm, left-right layout (this section's demo uses it)
cluster().size([h, w])Align all leaves to the same depth
treemap().tile(...)Area layout (slice-and-dice / squarified)
pack().radius(...) / partition()Circle packing / icicle·sunburst layout
3 ⭐ Key code
① hierarchy + tree: tree layout in three steps 
// 1. hierarchy: nested data → add parent / children / depth
const root = d3.hierarchy(rootData);

// 2. tree layout (Reingold–Tilford): compute x / y coordinates
const treeData = d3.tree().size([360, 720])(root);

// 3. links: parent-child lines; note the "swap" x=d.y, y=d.x
g.selectAll(".link").data(treeData.links()).join("path")
  .attr("d", d3.linkHorizontal().x(d => d.y).y(d => d.x));

// 4. nodes: translate each node to (y, x)
const ng = g.selectAll(".node").data(treeData.descendants()).join("g")
  .attr("transform", d => `translate(${d.y}, ${d.x})`);

treeData.x is the depth direction (vertical) and treeData.y is the horizontal direction (different nodes at the same depth). So in a horizontal tree, linkHorizontal must swap them as x = d.y, y = d.x; using d.x directly as the horizontal coordinate would misconnect the lines. This "x takes y, y takes x" swap is unique to horizontal trees.

② separation: controlling sibling spacing 
const treeLayout = d3.tree()
  .size([360, 720])
  .separation((a, b) => (a.parent === b.parent ? 1 : 2));
//                              ↑ siblings snug        ↑ different parents at least 2× apart

separation takes a function returning the "spacing multiplier" between two nodes. The default is 1 for siblings and 2 otherwise; tune it down to 0.5 and everything crowds together, up to 2.0 and the tree widens. It essentially adds one more constraint to the "position channel" — siblings must keep enough spacing.

③ Building a hierarchy tree from the rollup Map 
// recursively turn the nested Map into a plain { name, children } tree
function toTree(node, label) {
  if (node instanceof Map) {
    const children = [];
    for (const [k, v] of node) children.push(toTree(v, k));
    return { name: label, children };
  }
  return { name: `${label} (${node.length})` };   // leaf
}

const root = d3.hierarchy(toTree(nested, "Class of 2025"));

The previous section's rollup produces a nested Map, while this section's hierarchy wants { name, children }. This intermediate "recursive conversion" is the bridge from data transformation to visual mapping — once it's done, the tree's shape is fixed and all that remains is computing the positions.

Section summary

  • Visual mapping = choosing a channel for each data attribute; in the Mackinlay 1986 ranking, "position" is most accurate for all three data types, so tree layout prefers position.
  • Channels come in two kinds: magnitude channels (ordinal/quantitative, e.g. position, length) and identity channels (categorical, e.g. hue, shape); choosing the wrong kind misleads the reader.
  • The three Reingold–Tilford passes (bottom-up width measurement → top-down x assignment → handling threads) run in O(n) and are the core of d3.tree().
Self-test · Q1

In a horizontal tree (d3.tree().size([360, 720])), why does linkHorizontal().x(d => d.y).y(d => d.x) swap x and y?

d3.tree outputs x as the depth direction (vertical by default) and y as the horizontal direction (different nodes at the same depth). To make a horizontal tree, the horizontal direction must go to x and the depth direction to y — hence x = d.y, y = d.x inside linkHorizontal. Without this swap, the lines connect parents and children in the wrong direction.

Self-test · Q2

Mapping "major" (software engineering / data science, unordered) to hue and mapping "age" to position — which kind of channel does each use?

Major is a categorical attribute → use an identity channel (hue) to distinguish "which class"; age is a quantitative attribute → use a magnitude channel (position) to express "more vs less". Both picks are right: if age were crammed into hue instead, the reader couldn't tell who is older.

2.4 View Rendering and User Interaction

Turning the tree into a collapsible HTML list — tripping over click, bubbling, and delegation along the way, then adding the "time dimension" with animation.

1 Original case

Following the previous section, we have "visual structure". This section's 2.4 covers the last two arrows: "visual structure → views" (rendering) and "view ↔ user" (interactive feedback). The V layer of the Card model plus van Wijk's feedback loop both land here.

The original document used classed to control node styles and stopPropagation to block bubbling, focusing on turning the D3 tree-layout output into an interactive HTML list. This lesson turns "event bubbling" into a clickable, watchable tracing animation.

2 Embedded theory

The three phases of DOM events

The browser's event flow has three phases (DOM spec):

  1. Capturing: window → document → … → target element (outside in)
  2. Target: the target element itself
  3. Bubbling: target element → … → document → window (inside out)

By default, listeners fire in the bubbling phase. Calling e.stopPropagation() inside a listener cuts off bubbling so ancestors' listeners no longer fire.

Event delegation

Problem: a list has 1000 lis; binding a click listener to each li → slow, memory-heavy, and newly added elements need rebinding.
Solution: bind 1 click listener to the parent (ul) and let bubbling funnel everything to it; use e.target.closest('.label') to find "the child element actually clicked".
Benefit: 1 listener replaces N, and future elements are supported automatically.

Animation: the "time dimension" of view rendering

Animation (transition) isn't "flashy"; it's view rendering unfolding along the time dimension. D3 uses .transition().duration(ms) to smoothly interpolate attributes from old values to new ones. The teaching value centers on the single duration parameter:

  • duration = 0: an instant jump; the "process of change" is invisible;
  • duration = 500: a 0.5-second transition that clearly shows expanding / collapsing / moving smoothly;
  • duration > 1500: too slow; students start to zone out.
3 ⭐ Key code
① Event delegation: bind once on the parent, all children benefit 
// bind click only once, on the parent ul (event delegation)
ul.addEventListener("click", (e) => {
  const li = e.target.closest("li");   // find "the row actually clicked"
  if (!li || !ul.contains(li)) return;
  pick(li);                            // handle selection centrally
});

Binding 1 listener on each of 1000 lis → slow and memory-hungry; instead bind once on the parent and let bubbling funnel everything to it. e.target.closest("li") walks back from "the element actually clicked" to "the row we care about", so a click landing on an icon or text inside the row still hits correctly.

② The toggle-vs-select conflict: stopPropagation 
// collapse arrow: stop bubbling so the parent's "select" doesn't fire
label.addEventListener("click", (e) => {
  e.stopPropagation();       // ⭐ cut off bubbling
  node._collapsed = !node._collapsed;
  render();
});

// row select: only fired by "non-toggle" clicks
li.addEventListener("click", () => pick(li));

Without stopPropagation, clicking the collapse arrow would also trigger "select node", which confuses users. This is the core teaching point of the DOM event mechanism: one click, two listeners, divided by cutting off bubbling.

③ transition + duration: adding a time dimension to rendering 
svg.selectAll(".node")
  .transition()                          // enter the transition state
  .duration(DURATION)                  // duration (ms), controlled by the slider
  .attr("transform", d => `translate(${d.y}, ${d.x})`)
  .attr("opacity", 1);

// new nodes: set opacity=0 first, then transition to 1 → a fade-in effect
ng.attr("opacity", 0)
  .transition().duration(DURATION).attr("opacity", 1);

duration = 0 is an instant jump with no visible process; 500 makes expanding / collapsing clear; beyond 1500 it's too slow and people zone out. Animation turns "view rendering" from a single frame into a continuous process over time, and is the most intuitive embodiment of van Wijk's feedback loop.

Section summary

  • Three phases of DOM events: capturing (outside-in) → target → bubbling (inside-out); listeners fire in the bubbling phase by default.
  • Event delegation = 1 listener on the parent + e.target.closest() to locate the child; 1 listener replaces N, and new elements work automatically.
  • toggle and select are divided by stopPropagation() cutting off bubbling; an animation's duration is the "time dimension" of view rendering.
Self-test · 1 question

A list has 1000 lis and keeps growing. Compared with "binding a click to each li", what is the most essential benefit of event delegation?

Event delegation cuts the listener count from N to 1, and a newly inserted li naturally fires the parent listener through bubbling, with no per-item rebinding. It does not stop bubbling automatically, and telling "which row was clicked" still relies on e.target.closest("li").

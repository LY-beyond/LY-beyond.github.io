1.1 Data Generation

The starting point of every visualization: first pack the "real world" into a table.

1 Your original case

From start to finish this chapter uses a single dataset: the 2025 freshman roster of China University of Petroleum (East China). It was synthesized by the DeepSeek large model and contains 80 records and 8 columns.

Field list: the Chinese column names are for people to read, the JS variables are for the program to read
ColumnMeaningRaw typeSuggested JS type
序号Row number, a unique identifierStringNumber (id)
姓名Student nameStringString (name)
性别Male / FemaleStringString (gender)
生日Date of birthStringDate (birthday)
年龄Age at enrollmentStringNumber (age)
班级Software Engineering / Data Science + class numberStringString (class)
籍贯Province and cityStringString (hometown)
民族EthnicityStringString (ethnicity)
2 Embedded theory

The credibility limits of AI-synthesized data

Synthetic data is fine for teaching and practice, but it is not a substitute for real data. To assess whether any dataset is trustworthy, look at these four dimensions: accuracy (how well it reflects the real world), completeness (whether all fields are present), consistency (whether the same concept is expressed the same way everywhere) and timeliness (whether the data reflects the current state).

Sampling bias: the model tends to generate "plausible-looking" distributions — heavily skewed toward Han ethnicity and toward large cities for hometowns. So every conclusion in this chapter is meant only to demonstrate the method, and should not be extrapolated to real students.

3 ⭐ Key code
① Field-name mapping: Chinese column names → English JS variables 
// Map the Chinese CSV column names to English JS variables
const COLUMN_MAP = {
  "序号": "id", "姓名": "name", "性别": "gender",
  "生日": "birthday", "年龄": "age", "班级": "class",
};

Why not use Chinese keys? The JS engine is less tolerant of Chinese identifiers; backends, JSON and URL encoding may all introduce mojibake; and IDE completion, search and refactoring support for Chinese is inconsistent. Best practice: keep human-readable Chinese names in the CSV, and use English variables uniformly inside JS.

② Type conversion: turning strings into numbers and dates 
// Every row of data passes through this function
function transformRow(d) {
  return {
    id:       +d["序号"],              // unary +: the fastest way from string to Number
    name:     d["姓名"].trim(),       // trim() strips leading and trailing whitespace
    birthday: new Date(d["生日"]),    // string → Date object
    age:      +d["年龄"],
    class:    d["班级"].trim(),
  };
}

Pitfall: without trim(), the trailing space in "软件工程1班 " would make later filtering and aggregation "conjure up an extra class out of thin air". Safety net: new Date() handles "2007/8/15" poorly; to be safe, use d3.timeParse("%Y-%m-%d").

③ Passing the row callback directly as d3.csv's second argument 
// Load + convert row by row in one line
const data = await d3.csv("data/newstudent.csv", transformRow);

// Verify that the types were really converted:
console.log(typeof data[0].age);                // "number"
console.log(data[0].birthday instanceof Date); // true

Why this line matters: ① it is an async function, so you must await it; ② the row callback in the second argument is called right after each row is parsed, saving one full in-memory pass compared with "load first, then .map()"; ③ asynchronous loading does not block page rendering, so the user can keep interacting.

4 Runnable demo

Click "Reload" and watch the console output — focus on the two lines typeof data[0].age and birthday instanceof Date.

Section summary

  • Data credibility has four dimensions: accuracy, completeness, consistency and timeliness — synthetic data usually falls short only on "accuracy".
  • d3.csv(url, rowCallback) does loading and per-row conversion in one line, saving both memory and one full pass.
  • Keep Chinese column names in the CSV for people to read and English variables throughout JS for the program; trim() and the unary + are the two essential type-cleaning moves.
Self-test · 1 question

Passing a row callback as the second argument of d3.csv(url, transformRow), compared with "await first, then .map() to convert", has what main benefit?

The row callback is invoked the moment each row is parsed, so there is no need to read the whole string array into memory and then traverse it again. d3.csv is still asynchronous (await is required), and it neither renames columns nor converts types — you must do both yourself inside the callback.

1.2 Defining Data

The same "18" — is it three digits, a piece of information, or knowledge that can support a decision?

1 Your original case

The DIKW pyramid divides "from observation to decision" into four layers, each answering a different question:

LayerWhat it isQuestion it answersExample in this course
DataRaw, discrete observations— (no context yet)Row-by-row freshman records
InformationData that has been processed, organized and given contextWho / what / when / where"Software Engineering Class 1 averages 18.1 years old"
KnowledgePatterns and regularities further distilled from informationHow"Age is weakly correlated with major"
WisdomUsing knowledge to make wise judgments and strategic decisionsWhy / what should be done"Adjust admissions and training plans accordingly"
2 Embedded theory

Where visualization sits in DIKW

Key insight: visualization mainly lifts Data to Information; in a few scenarios it can reach Knowledge, but it rarely crosses over to Wisdom.

  • ✅ Data → Information: "translating" a table into readable graphics (line charts, bar charts, heatmaps).
  • ⚠️ Information → Knowledge: pattern discovery needs statistical models to help (such as machine learning).
  • ❌ Knowledge → Wisdom: decision-making and strategy are beyond the reach of visualization.

Rowley's (2007) critique: DIKW is an oversimplified hierarchical model. But as a teaching scaffold it is still the most valuable — it forces you to first ask "is what I have in hand data or information?"

3 ⭐ Key code
① SVG pyramid path: the three most-used commands M / L / Z 
// Trapezoid path: connect 4 points from top to bottom, then close
const topW = 60, botW = 120;
const yTop = 20, yBot = 100;
const path = `
  M ${cx - topW/2} ${yTop}
  L ${cx + topW/2} ${yTop}
  L ${cx + botW/2} ${yBot}
  L ${cx - botW/2} ${yBot}
  Z
`;

M (moveto) lifts the pen, L (lineto) draws a line, Z (close) closes the path — these three commands can draw the vast majority of diagrams. Template strings ${...} embed JS variables directly, far more readable than string concatenation.

② Events: why you must use function instead of an arrow function 
// ⚠️ function required: because the callback uses this to access the current element
svg.append("g")
  .on("mouseover", function () {
    d3.select(this).select("path")
      .transition().duration(150)
      .attr("fill", d3.color(layer.color).brighter(0.5));
  })
  .on("click", () => showDetail(layer));  // no this used, so an arrow function is fine

This is the most common D3 pitfall. An arrow function captures the outer this, so d3.select(this) selects the wrong element. As soon as this appears in a callback, it must be written as a function.

4 Runnable demo

Click any layer of the pyramid — the right side shows that layer's definition, typical visualizations and capability boundary.

Section summary

  • The four DIKW layers answer four different questions: Data (no context) → Information (who/what/when/where) → Knowledge (how) → Wisdom (why).
  • Visualization's main battlefield is Data → Information; going one layer higher relies on statistical models, not on "making the chart prettier".
  • Once this is used in a D3 event callback, you must write function and not an arrow function.
Self-test · 1 question

Drawing "80 rows of freshman records" as a "bar chart of the number of students per major" mainly accomplishes which transition in DIKW?

Aggregating context-free discrete records into "the number of students per major" and giving them the context of "major" and "count" is exactly Data → Information. To rise further to Knowledge you must distill patterns from the information (e.g. "Data Science majors tend to be older"), which looking at a chart alone cannot do.

1.3 Data Attributes

The "type" of data decides which visual channels you may use — the single most important rule in this chapter.

1 Your original case
CategoryExample in this courseNotes
CategoricalName, genderNo order relation
OrdinalClass, degreeOrdered but no fixed interval
NumericAge, exam scoreQuantitative; supports +, −, ×, ÷
2 Embedded theory

Stevens' scales of measurement (1946): the 4 finer categories beyond your original text

ScaleAllowed operationsTypical examplesOriginal category
NominalEquality / inequalityName, genderCategorical
OrdinalComparing magnitude (> <)Rank, class numberOrdinal
IntervalAddition and subtraction, but not × ÷Temperature (°C)—
RatioAll of +, −, ×, ÷ allowedAge, priceNumeric

Key difference: an interval scale has no "true zero" (0°C is not "no temperature"), while a ratio scale does (0 yuan = no money).

Mackinlay's ranking of visual channels (1986)

Visual channels are divided by "the type of information they can carry" into three tiers: quantitative (position, length, angle) suits ratio / interval; ordered (luminance, density, saturation) suits ordinal; qualitative (hue, shape) suits nominal.

Mapping ratio data (such as age) to hue is the most common mismatch: a rainbow hue is neither continuous nor CVD-friendly, so readers cannot judge magnitude from color. Likewise, putting nominal data (such as major) onto a position axis to sort it conjures an ordering that does not exist.

3 ⭐ Key code
① Choosing a scale: mapping attributes ↔ channels 
// ratio / interval data → scaleLinear (continuous quantitative)
const x = d3.scaleLinear().domain([0, 100]).range([0, 800]);

// nominal / ordinal data → scaleBand (discrete categorical)
const x = d3.scaleBand()
  .domain(["软件1班", "软件2班", "数据1班"])
  .range([0, 800]);

domain() is the data domain (input), range() is the value range (output pixels). Picking the wrong scale is beginners' most common mistake: using scaleLinear for categorical data produces meaningless intermediate values like "0.5 of a class".
Rule of thumb: continuous quantitative → Linear, discrete categorical → Band, and ordinal → Point works too.

② Choosing a colormap: sequential / qualitative / diverging 
// sequential (order is meaningful) → Viridis, CVD-friendly and perceptually uniform
const color = d3.scaleSequential(d3.interpolateViridis);

// qualitative (no order) → schemeTableau10
const color = d3.scaleOrdinal().range(d3.schemeTableau10);

// diverging (has a midpoint) → RdBu
const color = d3.scaleDiverging(d3.interpolateRdBu);

Common mistake: using the rainbow interpolateRainbow to encode numeric values — it is not CVD-friendly, and it fabricates non-existent "false boundaries" at hue turns. When to use a diverging scale: when the data has a clear midpoint (positive/negative, or temperature relative to an average).

4 Runnable demo

The first three are correct "attribute → channel" matches; the fourth is a deliberate mistake for contrast — compare them and you will see exactly what a "mismatch" throws away.

Section summary

  • Stevens' 4 scales: nominal (equality), ordinal (comparison), interval (add/subtract, no true zero), ratio (has a true zero).
  • Mackinlay's 3 channel tiers: quantitative (position/length/angle), ordered (luminance/density/saturation), qualitative (hue/shape).
  • Matching rules: ratio/interval → quantitative channels; ordinal → ordered channels; nominal → qualitative channels. A mismatch directly loses information.
Self-test · Question 1

"Major" (Software Engineering / Data Science) is a nominal scale. According to the matching matrix, which class of visual channel is it best mapped to?

A nominal scale has no order, so you can only use channels that express categorical difference — hue (qualitative) is the first choice. Using luminance would imply an order that does not exist; sorting by position would fabricate a false relation like "Software Engineering > Data Science".

Self-test · Question 2

"0°C does not mean there is no temperature." What does this say about which of Stevens' scales temperature belongs to?

An interval scale has no true zero, so you can compare differences (20°C is 10°C higher than 10°C) but cannot say "20°C is twice 10°C". Only ratio scales (such as age and price) have a true zero and thus allow multiplication and division.

1.4 Data Transformation

D3's 8 array functions: turning "raw data" into "data you can draw".

1 Your original case
#FunctionPurposeAnalogy
1map(iterable, mapper)Element-wise transformArray.map
2reduce(iterable, reducer, init)Reduce to a single valueArray.reduce
3cross(...iterables, reducer)Cartesian product—
4merge(iterables)Merge into a flattened arrayArray.flat
5pairs(iterable, reducer)Adjacent element pairs—
6transpose(matrix)Matrix transpose—
7zip(...arrays)Position-wise merge—
8filter(iterable, test)Filter by a conditionArray.filter
2 Embedded theory

Functional data flow

These 8 functions share three traits: immutable (the input is unchanged, a new array is returned), pure (same input → same output) and chainable (the return value is still an array, so it can feed the next transformation).

  • Why functional? Reasonable (each layer is independently testable), parallelizable (map/reduce are naturally parallel) and cacheable (pure functions can be memoized).
  • Relation to OLAP: transpose converts between wide and long formats, while group + rollup perform slice, dice and drill-down — this is the germ of the data cube.
3 ⭐ Key code
① map / filter / reduce chained together 
// One chain computes "the average age of boys"
const boys = students.filter(s => s.gender === "男");
const avgAge = boys
  .map(s => s.age)                     // ② extract age
  .reduce((sum, a) => sum + a, 0) / boys.length;  // ③ sum then average

Each step of the chain returns a new array and never mutates the original. Contrast with the imperative style: that needs four temporary variables plus a for loop, whereas the functional version does it in one line. Performance trade-off: every map/filter creates a new array, which only becomes noticeable for arrays in the millions or more.

② cross: the Cartesian product 
const genders = ["男", "女"];
const majors  = ["软件工程", "数据科学"];
const combos  = d3.cross(genders, majors);
// → [["男","软件工程"], ["男","数据科学"],
//    ["女","软件工程"], ["女","数据科学"]]

The Cartesian product is often used for pairwise-combination analysis (counting people by gender × major). The optional second argument, the reducer, first merges the two elements into one. Size warning: the Cartesian product of n arrays has a size equal to the product of their lengths, so it can explode quickly.

③ group and rollup: keep groups vs aggregate groups 
// group: returns a Map, keeping all elements under each key
const byClass = d3.group(students, s => s.class);

// rollup: returns a Map, keeping only the aggregated value under each key
const countByClass = d3.rollup(
  students,
  v => v.length,     // reducer
  s => s.class       // key extractor
);

In one sentence: group keeps the groups, rollup aggregates them. The second argument of rollup is the reducer (here, taking the length). A later chapter, Chapter 2, uses it to turn a flat table into tree-structured data.

4 Runnable demo

Switch the dropdown to pick a function — the "data-flow pipe" above lights up the matching segment, and below you see the input and output.

Section summary

  • D3's array functions are immutable + pure + chainable, so you can process data layer by layer like a pipe.
  • map reshapes, filter picks a subset, reduce reduces to a value; chaining the three gives the most common data-cleaning pipeline.
  • group keeps the elements of each group, rollup keeps only the aggregate — the former builds trees, the latter builds summaries.
Self-test · 1 question

To count "how many people are in each class" while also keeping each class's student list for later drill-down, which should you use?

Every key in the Map returned by group retains the full array of elements, so you can both count with v.length and keep reading the list. rollup discards the elements and keeps only the aggregate — more compact, but no longer drill-down-able.

1.5 D3 Data Selectors

The core of D3 is not "drawing" but "binding data to the DOM and, when the data changes, working out what to add, change or remove".

1 Your original case
MethodReturns
d3.selectA single element
d3.selectAllA selection of multiple elements
selection.selectThe first descendant of each selected element
selection.selectAllAll matching elements among the descendants
selection.selectChildThe first direct child
selection.selectChildrenAll direct children
2 Embedded theory

The three-state Data-Join model

Bind a data array to DOM elements; when the data changes, the extra, the matching and the surplus elements fall into three separate sets:

  • new data > old elements → enter: new elements need to be appended (green in the demo).
  • new data = old elements → update: attributes need to be changed (blue in the demo).
  • new data < old elements → exit: old elements need to be removed (red in the demo).
3 ⭐ Key code
① .join(enter, update, exit): the three states 
const circles = svg.selectAll("circle")
  .data(currentData)
  .join(
    enter  => enter.append("circle").attr("fill", "green"),  // added
    update => update.attr("fill", "cyan"),                 // updated
    exit   => exit.remove()                                  // removed
  );

join's three callbacks are invoked in the enter / update / exit stages respectively, which is more concise than v3's enter().append() + exit().remove() and far less likely to miss a branch. Analogy: this is React's diff + patch — except React does it for you, while D3 makes you write the transformation functions yourself.

② The key function: a stabilizer for element identity 
// ❌ without a key: binding by index; a data reorder → everything becomes "update", animation breaks
svg.selectAll("circle").data(newData);

// ✅ with a key: bind identity using a unique field
svg.selectAll("circle").data(newData, d => d.id);
// exactly the same idea as React's key={item.id}

Without a key, D3 binds identity by index; as soon as the data is reordered, every element "swaps places" and the transition looks like the whole row was redrawn. With a key, each element knows its own id, and a reorder is just a change in cx, so the animation flows naturally.

③ select vs selectAll 
// select: operates on just 1 element (the first match)
const title = d3.select("#title");

// selectAll: binds data in bulk, one-to-one in order
const bars = d3.selectAll(".bar").data(values);

select is for "operating on a single element", selectAll for "binding data in bulk". Best practice: first use selectAll to create a placeholder selection (which may be empty), then .data().join(...) — this is exactly why enter exists.

4 Runnable demo

Click the three buttons to trigger enter / update / exit respectively, and watch how the dots' colors and positions change.

Section summary

  • The three states of Data-Join: more new data → enter (append), matching → update (change attributes), more old elements → exit (remove).
  • .join(e, u, x) handles all three states in one method, so it is harder to miss a branch than hand-writing enter/exit.
  • The key function (.data(d, d => d.id)) keeps elements' identity after a reorder — the precondition for natural transition animations.
Self-test · 1 question

Data changes from [1, 2, 3] to [3, 2, 1] (only the order changes). If no key function is provided when binding, what happens?

The number of elements is unchanged (still 3), so neither enter nor exit applies. But without a key, D3 binds identity by index, so each circle thinks "my data changed" and all go through update — no elements are added or removed, yet the animation looks like the whole row was redrawn. Add d => d.id and it returns to normal.

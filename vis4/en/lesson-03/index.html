3.1 Color model basics

Why do we need four color spaces? What is each of them good at? And what does the world look like to a color-blind viewer?

1 Your original case

This chapter uses exactly one dataset from beginning to end: crime statistics by U.S. state (data/crime.csv), with 50 states and 13 columns (population, robbery, murder, arson, and so on). The data itself is not the point — the point is that with the same data, swapping the palette changes how readers understand it entirely.

The four palette questions of this chapter, mapped to four knowledge blocks
QuestionAnswered inKey conclusion
Can colors simply be interpolated in RGB?3.1 / 3.3No — RGB is not perceptually uniform; interpolate in CIE Lab
Which kind of color scale for continuous values?3.2Ordered → sequential; has a midpoint → diverging; unordered → qualitative
A few categories — how to combine colors without glare?3.4 / 3.7≤ 7 categories; hues at least 30° apart; supporting colors S 30–50%
Can color-blind readers still follow it?3.5 / 3.8Check yourself with CVD simulation; red-green contrast is the most dangerous

For example, plot each state's murder (murder count) as a bar chart: with “light blue → dark blue” readers can read magnitude; with a “red → yellow → green” rainbow scale they only see a patchwork of colors — the yellow in the middle is neither the “maximum” nor the “minimum”, it carries no semantics at all.

2 Embedded theory

Four color spaces, four kinds of “good at”

SpaceModelGood atPerceptually uniform?
RGBAdditive (three beams of light added together)How screens emit light, native device storage✗ No
HSLHue / Saturation / LightnessIntuitive color picking for people (designers especially)✗ No
CIE LabL* lightness + a* / b* opponent channelsMeasuring “how different it looks”✓ Yes (gold standard)
CMYKSubtractive (ink absorbs light)Printing / publishing✗ No

Core conclusion: RGB is the “device space”, Lab is the “thinking space”. When designing a colormap you interpolate in Lab and clamp only when converting to RGB for display — which is why gradients from d3.interpolateLab are smoother than those from d3.interpolateRgb.

CVD (color vision deficiency): about 8% of men and 0.5% of women have some color vision deficiency. The three common types are protanopia (red-blind, about 1% of men), deuteranopia (green-blind, about 6% of men, the most common), and tritanopia (blue-blind, extremely rare). In other words, one page of your slides almost certainly has at least one reader who cannot tell red from green.

3 ⭐ Key code
① RGB → HSL by hand: the largest channel decides the hue 
// input 0-255, output h∈[0,360) s,l∈[0,100]
function rgbToHsl(r, g, b) {
  r /= 255; g /= 255; b /= 255;
  const max = Math.max(r, g, b), min = Math.min(r, g, b);
  let h, s, l = (max + min) / 2;
  if (max === min) { h = s = 0; }          // grey: no hue
  else {
    const d = max - min;                     // max − min → saturation
    s = l > 0.5 ? d / (2 - max - min) : d / (max + min);
    switch (max) {                          // whichever is largest → decides where the hue lands
      case r: h = (g - b) / d + (g < b ? 6 : 0); break;
      case g: h = (b - r) / d + 2; break;
      case b: h = (r - g) / d + 4; break;
    }
    h /= 6;
  }
  return [h * 360, s * 100, l * 100];
}

Writing it out yourself is how the three physical steps become clear: the largest channel decides the hue, max minus min decides the saturation, and max plus min decides the lightness. It also explains why hue is a 0–360° circular quantity — when adding an offset you must use (h + 30 + 360) % 360 so it never runs off.

② CVD simulation: one line of matrix multiplication swaps a pair of eyes 
// A Machado-2009-style approximation matrix: multiply RGB once and you get the color "seen by a color-blind eye"
const CVD_MATRICES = {
  protanopia:   [[0.567, 0.433, 0], [0.558, 0.442, 0], [0, 0.242, 0.758]],
  deuteranopia: [[0.625, 0.375, 0], [0.700, 0.300, 0], [0, 0.300, 0.700]],
  tritanopia:   [[0.950, 0.050, 0], [0, 0.433, 0.567], [0, 0.475, 0.525]],
};

function simulateCVD([r, g, b], type) {
  const m = CVD_MATRICES[type];
  return [
    r * m[0][0] + g * m[0][1] + b * m[0][2],
    r * m[1][0] + g * m[1][1] + b * m[1][2],
    r * m[2][0] + g * m[2][1] + b * m[2][2],
  ].map((v) => Math.max(0, Math.min(255, v)));
}

All three deficiencies are linear transforms: the responses of the three cone types are simply “merged”. The matrices show at a glance why deuteranopia is the most dangerous — the first row 0.625 / 0.375 and the second row 0.700 / 0.300 are almost identical, so red and green are projected onto nearly the same direction.

③ How we do it here: colors always come from design tokens 
// This site builds nothing and works offline, so it pulls in no D3 and no color library;
// when "real color numbers" are needed, read them out of the CSS design tokens and compute.
const token = (name) =>
  getComputedStyle(document.documentElement).getPropertyValue(name).trim();

const rgb = parseColorCss(token('--c-primary'));   // → [67, 56, 202]
const hsl = rgbToHsl(...rgb);                      // then do hue rotation, Lab conversion…

Three benefits: ① no hard-coded color values appear anywhere in the page, so re-theming touches only tokens.css; ② after switching to dark mode the demos adapt automatically (tokens hold a different set of values in the dark theme); ③ demos and inline figures share one palette, so what is explained and what is seen match exactly.

Section summary

  • RGB is the device space, HSL the intuitive space, CIE Lab the perceptual space, CMYK the print space — design colormaps by interpolating in Lab.
  • Hue is a 0–360° circular quantity, so any offset must take mod 360; saturation comes from “max minus min”.
  • About 8% of men have a color vision deficiency, deuteranopia being the most common — a palette must pass the CVD test (there is a simulator in 3.8).
Self-check · 1 question

To design a colormap gradient that is smooth with a natural light-to-dark transition, in which color space should you interpolate?

Neither RGB nor HSL is perceptually uniform: interpolating linearly in RGB produces a fake step in the middle that “looks darker/brighter than both ends”. Euclidean distance in CIE Lab ≈ perceived difference, so a gradient built with equal steps in Lab looks like equal steps to a human eye — that is the reason d3.interpolateLab exists.

3.2 Choosing among the three colormap families

Sequential / diverging / qualitative — picking the wrong family is not “ugly”, it misleads the reader.

1 Your original case
Three colormap families for three kinds of data semantics
FamilyData semanticsColor characteristicsTypical schemes
SequentialA natural order: population, temperature, murder countMonotone lightness + monotone hueViridis / Plasma / Cividis
DivergingA genuine, meaningful midpoint: 0, positive/negative deviation, relative to the medianDifferent colors at the two ends, lightest in the middleRdBu / BrBG / PiYG
QualitativeUnordered categories: states, product lines, experimental groupsHues widely separated, lightnesses closeTableau10 / Set1 / Okabe–Ito

Back to crime.csv: murder is a value with a “natural order” → sequential; if you first compute “each state's murder rate minus that state's historical mean”, the difference is positive or negative and 0 is meaningful → diverging; if you only want to tell 5 regions' categories apart → qualitative.

2 Embedded theory

Picking the wrong family = lying

Use the diverging RdBu to plot the ordered “murder rate of 50 states”: the middle of the scale is nearly white, and readers instinctively read the “nearly white” states as “middling, normal” — but the value 100 has no such semantics at all; it is pure misdirection. Conversely, use the sequential Viridis to show a positive/negative deviation and readers will assume the white area is the zero point, when Viridis's midpoint is in fact a deep purple. So ask about the data semantics first, and only then pick the scale family.

CVD-friendly checklist: Viridis / Cividis ✅ good (recommended by Nature Methods); RdBu / BrBG △ fair (the red and green ends are unfriendly to color-blind readers); Tableau10 △ hue-dependent; Jet / Rainbow ⚠ outright banned.

3 ⭐ Key code
① A quick mnemonic for the three scale types 
// sequential: [0, 1] → color (monotone lightness)
const seq = d3.scaleSequential(d3.interpolateViridis);

// diverging: t=0 one end, t=0.5 the midpoint, t=1 the other end
const div = d3.interpolateRdBu;

// qualitative: category → color (they must not sit next to each other or they clash)
const cat = d3.scaleOrdinal(d3.schemeTableau10);

The three share exactly the same interface (input [0,1], output a color); the only difference is the semantic contract: sequential promises “larger is darker”, diverging promises “lightest at the midpoint”, qualitative promises “similar lightness”. As soon as a contract is used on data that does not satisfy its premise, the colors start lying.

② Decision table: ask the data first, then pick the scale 
function pickColormap(data) {
  if (data.hasMeaningfulMidpoint) return 'diverging';   // has a true midpoint (0 / mean)
  if (data.isOrdered)              return 'sequential';  // has a natural order
  return 'categorical';                                  // otherwise: unordered categories
}

The order of the two questions cannot be swapped: “does 0 mean anything” comes before “is the data ordered”. Data that is ordered but has 0 as its midpoint (month-over-month growth, say) should go to diverging — this is precisely the watershed between the murder rate and the “murder-rate deviation” in crime.csv.

③ How we do it here: compute the gradient by mixing tokens 
// sequential: step from "5% primary + 95% surface" to "100% primary", mixing level by level
const cells = 16;
for (let i = 0; i < cells; i++) {
  const p = Math.round(i / (cells - 1) * 100);
  strip.append(el.style.background =
    `color-mix(in srgb, var(--c-primary) ${p}%, var(--c-surface))`);
}

// diverging: left half danger color → surface color, right half surface color → primary
// the midpoint naturally lands on "surface color", matching the semantics of "midpoint = 0"

Why not a hard-coded array of hex values: this site has to support light and dark themes. var(--c-primary) is indigo on a light background and pale indigo on a dark one, and var(--c-surface) changes with it — the whole scale computed by mixing adapts to the theme automatically, something hard-coded hex cannot do.

4 Runnable demo

The three strips above are computed (the sequential and diverging ones are generated level by level by mixing tokens — they are not images); below, the murder counts from crime.csv are drawn as a real bar chart, and you can switch between “sequential / diverging” to see how diverging tells the story of ordered data wrong.

Section summary

  • Each colormap family matches one kind of data semantics: ordered → sequential, genuine midpoint → diverging, unordered categories → qualitative.
  • Picking the wrong family is not an aesthetic issue: diverging on ordered data invents a “normal midpoint” out of nothing, and sequential on a positive/negative deviation makes people mistake deep purple for the zero point.
  • The rainbow family (Jet) is none of the three: not perceptually uniform, unfriendly to CVD, unfriendly to print — it should simply be banned.
Self-check · 1 question

One dataset is “each state's crime rate relative to the U.S. median” (positive and negative, with 0 as a meaningful midpoint). Which colormap family fits best?

Deviation data has a “midpoint 0” with clear semantics, so you want diverging: lightest at the midpoint, different colors at the ends, and readers see at a glance whether a state is “above the median” or “below the median” and by how much. Sequential would hide the 0 in the middle of the scale, while qualitative would throw away the degree of the deviation.

3.3 The CIE Lab gamut diagram

In a perceptually uniform color space, what exactly do “the colors a display can show” look like?

1 Your original case

You want to give crime.csv a “highly saturated pure green → pure red” scale. The colors you compute in Lab look lovely, but the green rendered on an LCD screen comes out “muted” — because the green you computed has run outside the screen's gamut.

GamutStandard / scenarioRelative sizeUse in this course
sRGBWeb / PPT / general scientific figuresSmallest (baseline)The target gamut of this rebuild
Adobe RGBPhotography / printMedium (wider green region)Worth noting when submitting a print version
Rec.20204K / HDR televisionLargestOut of reach for the web today
2 Embedded theory

Why “nested”, and why it gets clamped

The three gamuts are nested: sRGB ⊂ Adobe RGB ⊂ Rec.2020. If a color computed from Lab coordinates falls outside sRGB, the standard conversion pipeline clamps it back to the sRGB boundary — the result is not an error but “the color looks different”, and it changes without your noticing at all.

Three practical points: ① d3.lab(L, a, b).rgb() clamps silently; ② when designing a colormap use d3.interpolateLab, which is smoother than interpolateRgb; ③ highly saturated colors “really exist” only on print / 4K screens, and may not be accurate on the web.

3 ⭐ Key code
① Lab ↔ sRGB: only without clamping can you detect out-of-gamut 
// γ decode: sRGB value → linear light
const toLinear = (v) => (v /= 255) <= 0.04045
  ? v / 12.92 : Math.pow((v + 0.055) / 1.055, 2.4);

function labToRgb(L, a, b) {
  const fy = (L + 16) / 116;                     // Lab → XYZ (D65 white point)
  const fx = a / 500 + fy, fz = fy - b / 200;
  const xyz = [fx * fx * fx * 0.95047, fy * fy * fy, fz * fz * fz];
  // XYZ → linear RGB (the inverse of the standard sRGB matrix)
  const lin = xyzToLinearSrgb(xyz);
  // note: we deliberately do NOT clamp here — out-of-range values stay as they are, so we can tell whether the color is out of gamut
  return lin.map((v) => v <= 0.0031308
    ? v * 12.92 : 1.055 * Math.pow(v, 1 / 2.4) - 0.055) .map((v) => v * 255);
}

The crux is precisely this “do not clamp” step. If the conversion function clipped its result into [0,255] internally, you would never discover that a color you computed has left sRGB. The demo here uses “convert without clamping, then test afterwards” to find the gamut boundary, and the boundary line it draws is obtained exactly that way.

② Testing whether a color is in gamut (and finding the boundary along the way) 
// in gamut ⟺ all three channels lie in [0, 255] (with a little float tolerance)
const inGamut = (rgb) => rgb.every((v) => v >= -0.5 && v <= 255.5);

// how to find the boundary: fix L* and, along each hue angle, binary-search for "the farthest radius still in gamut"
function outline(L, angles = 180) {
  const pts = [];
  for (let i = 0; i < angles; i++) {
    const th = i / angles * Math.PI * 2;
    let lo = 0, hi = 200;                 // 18 bisections are enough to locate it
    for (let k = 0; k < 18; k++) {
      const mid = (lo + hi) / 2;
      if (inGamut(labToRgb(L, mid * Math.cos(th), mid * Math.sin(th)))) lo = mid; else hi = mid;
    }
    pts.push([lo * Math.cos(th), lo * Math.sin(th)]);
  }
  return pts;                                  // connect them and you have the gamut polygon
}

The same labToRgb + inGamut pair does three jobs: telling whether a color can be displayed, finding the shape of the gamut boundary, and comparing the size difference between sRGB and Adobe RGB (the three nested outlines in the demo come from exactly this).

③ Interpolating in Lab vs. interpolating in RGB 
// ✅ interpolate in Lab: the middle point is perceptually "the true middle"
const mid = rgb2lab(mix(rgb2lab(c1), rgb2lab(c2), 0.5));

// ❌ linear interpolation straight in RGB: the middle sags (looks darker)
const bad = [c1, c2].map((c, i) => c * (1 - i) + c * i);

// the two corresponding functions in d3 (c1, c2 being any two endpoint colors)
// d3.interpolateLab(c1, c2)(0.5)   ← perceptually uniform
// d3.interpolateRgb(c1, c2)(0.5)   ← not the perceptual midpoint

The three nested gamuts and the array of in-gamut color patches in the demo are all computed live (not images), so when you drag L* you can watch the gamut area shrink as a whole — which is the visual evidence for the statement “dark colors have a narrower saturable range”.

4 Runnable demo

Drag the L* slider to watch the gamut shrink; drag the sample point on the diagram with the mouse and the right side reads out its Lab values and whether it is “inside sRGB”. Tick the outer two layers to see the relative sizes of Adobe RGB / Rec.2020.

Section summary

  • Gamuts are nested: sRGB ⊂ Adobe RGB ⊂ Rec.2020; a color computed in Lab may fall outside sRGB.
  • Colors beyond sRGB are silently clamped back to the boundary — no error, just a color that “quietly changed”.
  • For a smooth gradient interpolate in Lab, and let the browser clamp when converting to RGB for display; to judge “can it be displayed” you must first convert without clamping.
Self-check · 1 question

You construct a highly saturated pure green in Lab (outside sRGB) and then convert it to RGB to display on an ordinary LCD. What happens?

The conversion pipeline squeezes each channel into [0, 1] and simply discards the excess — so “an oversaturated green” becomes “the most saturated green sRGB can express”. Nothing is reported, so the only way to catch it in advance is the gamut diagram of this section: the green sample point has crossed the sRGB outline.

3.4 Color harmony rules (5 families)

Monochromatic / analogous / complementary / triadic / split-complementary — when should you use which?

1 Your original case

Still crime.csv: you plan to draw the four regions “Northeast / Midwest / South / West” as four groups of bars. Four categories, no order — so now you have to “pick angles” on the color wheel: pick the wrong angles and the four groups of bars fight each other; pick the right ones and it clicks with the legend at a glance.

RuleHue relationshipCharacteristicsWhen to use
MonochromaticOne hue, changing only lightness / saturationSafest, least glaringSerious scientific figures (Nature-style economical palettes)
AnalogousAdjacent on the color wheel, ±30°Harmonious, but weak contrastExpressing “hierarchy / grouping”
ComplementaryOpposite on the color wheel, 180°Strongest contrast, easily glaringHighlighting: treatment group vs. control group
Triadic120° apart on the color wheelAll three colors separate cleanly from one anotherExactly 3 categories
Split-complementary150° to either side of the oppositeA gentler version of complementaryThe default choice when unsure
2 Embedded theory

After picking the angles, you still have to pass “readability”

Whether a color combination looks good is a question of hue difference; whether text can be read is a question of contrast — and the latter can be quantified with the WCAG contrast formula: contrast = (L1 + 0.05) / (L2 + 0.05), where L is relative luminance.

WCAG 2.1 levelBody text (~14px regular)Large text (≥18.66px bold / ≥24px)
AA≥ 4.5 : 1≥ 3 : 1
AAA≥ 7 : 1≥ 4.5 : 1

The most common trap: using “complementary colors” directly as “text color + background color”. Complementary colors sit 180° apart in hue, but their luminance may be very close — however large the hue difference, the contrast may be only 2:1 and the text reads as a blur. Hue difference governs “can they be told apart”, luminance difference governs “can they be read”.

3 ⭐ Key code
① The essence of the five families: a set of hue offsets 
const HUE_OFFSETS = {
  monochromatic: 0,    // same hue, only S / L change
  analogous:     30,   // adjacent ±30°
  triadic:       120,  // triadic
  split:         150,  // split-complementary
  complementary: 180,  // opposite
};

function swatches(baseH, offset, n = 5) {
  return Array.from({ length: n }, (_, i) => {
    const h = (baseH + i * offset + 360) % 360;   // ← mod 360 must not be forgotten
    return hsl2rgb(h, 60, 55);                     // convert to RGB and draw directly
  });
}

The five rules differ in only one parameter: the hue difference between neighboring colors. Remember that sentence and you don't have to memorize five blocks of code — 0 / 30 / 120 / 150 / 180 is all of it.

② WCAG contrast: turning “can't read it” into a number 
// relative luminance: γ-decode first, then weight and sum (the eye is most sensitive to green)
function luminance([r, g, b]) {
  const lin = [r, g, b].map((v) => {
    v /= 255;
    return v <= 0.03928 ? v / 12.92 : Math.pow((v + 0.055) / 1.055, 2.4);
  });
  return 0.2126 * lin[0] + 0.7152 * lin[1] + 0.0722 * lin[2];
}

// contrast ratio: always "brighter over darker", so the result is ≥ 1
const ratio = (c1, c2) => {
  const [a, b] = [luminance(c1), luminance(c2)].sort((x, y) => y - x);
  return (a + 0.05) / (b + 0.05);
};

Three thresholds are all you need to remember: 3 : 1 (large text AA / boundaries of graphical elements), 4.5 : 1 (body text AA), 7 : 1 (body text AAA). The verdicts in the demo are exactly these three numbers being compared.

③ Using contrast to constrain the palette in reverse 
// generate candidate colors by the harmony rules, then filter out those that cannot serve as text
function pickTextColor(bg, candidates) {
  const ok = candidates.filter((c) => ratio(bg, c) >= 4.5);
  if (ok.length) return ok[0];
  // none qualifies → don't change the color, change the background (or switch to large, bold text)
  return null;
}

The palette workflow should be “decide the semantic hue first, then converge on contrast”. The other way round (pick pretty colors first, worry about readability later) is exposed by the demo in one calculation: many “pretty complementary pairs” have a body-text contrast of only 2–3 : 1.

Section summary

  • The five harmony rules differ in one parameter only: the hue difference between neighbors, 0 / 30 / 120 / 150 / 180, for monochromatic / analogous / triadic / split-complementary / complementary.
  • How to choose: monochromatic for serious science, analogous for grouping, complementary to highlight, triadic when there are exactly 3 categories, split-complementary when unsure.
  • Hue difference decides “can they be told apart”, luminance difference decides “can they be read”; the AA threshold is 4.5 : 1 for body text and 3 : 1 for large text.
Self-check · 1 question

What minimum contrast does WCAG 2.1 require at level AA for “body text” (about 14px at regular weight)?

4.5 : 1 is the threshold for body text at AA; 3 : 1 is the standard for large text at AA (and for the boundaries of graphical elements); 7 : 1 is what body text needs for AAA. Don't mix up the three numbers — the verdict labels in the demo are given live against exactly these thresholds.

3.5 Classic scientific palettes

Wong / Paul Tol / Okabe–Ito / Tableau / Paired / Viridis — which set are top journals actually using?

1 Your original case

You draw a five-region comparison chart from crime.csv and need 5 colors. There are too many options: Tableau 10 is attractive, Paired 12 has a full set, rainbow is the most “eye-catching” — but what top journals actually use are those palettes that look “a bit dull”. Why?

PaletteSourceColorsCharacteristics / risks
Wong 2011Nature Methods 8:4418CVD-friendly + grayscale-print friendly
Okabe–ItoOkabe & Ito 20028Early Nature / Science default; this course's --ch-1..8
Paul TolSRON Tech Note7~8Provides bright / muted / high-contrast versions for three scenarios
Tableau 10Tableau commercial default10Generally attractive, but red-green is unfriendly to color-blind readers

2 Embedded theory

The three hard criteria journals use to pick a palette

  • Category count ≤ 7: beyond 7 the eye can no longer tell them apart — with many categories, switch to a continuous colormap or use small multiples.
  • Passes CVD simulation: still distinguishable from the protanopia / deuteranopia / tritanopia viewpoints (see 3.8).
  • Distinguishable in grayscale: papers are often printed in black and white, so after converting the colors to lightness they must still be distinguishable. This criterion rules out a great many pretty palettes with “different hues, identical lightness”.

That is why Okabe–Ito / Wong style palettes look “not vivid enough”: it is precisely to satisfy the three criteria above that they pull the hues apart while also deliberately drawing out a lightness gradient.

3 ⭐ Key code
① Define palettes with tokens instead of hard-coded hex 
// ❌ old style: hard-copy 8 hex values into the JS, so nothing moves when the theme changes
// const WONG = ['<hex-1>', '<hex-2>', ... ];

// ✅ our style: a palette = a set of design tokens (mixing allowed)
const SCHEMES = {
  'course qualitative': ['var(--ch-1)', 'var(--ch-2)', 'var(--ch-3)', 'var(--ch-4)'],
  'primary ramp':   [100, 74, 52, 34].map(
    (p) => `color-mix(in srgb, var(--c-primary) ${p}%, var(--c-surface))`),
};

A palette itself becomes “a combination of tokens”, and the benefit is one-click switching between light and dark themes: in dark mode --ch-1..8 are a specially brightened set, since a palette that reads well on a light background is often too dark on a dark one — tokens solve that automatically.

② Grayscale friendliness self-check: convert to lightness and sort 
// sort every color of the palette by WCAG relative luminance,
// then check whether the luminance gap between adjacent colors is large enough
// — too small ⇒ everything blurs together when printed in black and white
const lums = palette.map(luminance);
const gaps = lums.slice(1).map((v, i) => Math.abs(v - lums[i]));
const minGap = Math.min(...gaps);           // rule of thumb: ≥ 0.06 is fairly safe
const grayscaleSafe = minGap >= 0.06;

luminance() is the same WCAG formula as in 3.4: one function, two uses — judging text contrast and judging grayscale-print distinguishability. This is also why “top-journal palettes look plain”: to get the luminance gaps they give up part of their freedom in hue.

③ A fallback when the category count overshoots 
// categories ≤ 7: use a qualitative palette; 8–10: a qualitative palette just about works but must pass CVD;
// > 10: switch to "continuous colormap + ordering" or small multiples, don't force in more colors
function paletteFor(n) {
  if (n <= 8) return { type: 'qualitative', note: 'just pass the CVD and grayscale checks' };
  if (n <= 12) return { type: 'qualitative+', note: 'borderline; better to merge categories first' };
  return { type: 'redesign', note: 'switch to a continuous colormap / small multiples / grouping' };
}

Do not force “one color per category”. Better moves are: merge the minor categories into “other”, split one chart into small multiples, or simply map categories onto position (facets) instead of color.

Self-check · 1 question

Top journals have largely switched to “plain-looking” palettes such as Okabe–Ito / Wong. What is the most central reason?

These palettes constrain hue difference and luminance gradient at the same time by design: pulling the hues apart keeps CVD readers able to distinguish, and pulling the luminance apart keeps them distinguishable after conversion to grayscale. On screen they are indeed less “attention-grabbing” than a rainbow, but for a paper that may be printed in black and white and read by color-blind readers, those two constraints matter far more than “looking good”.

2 Embedded theory

Why “rainbow” is outright banned by top journals

A rainbow scale has a cyclic hue, and the human eye's perception of lightness is not monotone across the blue→green→yellow stretch: a single gently rising dataset drawn in rainbow shows a patch in the middle that “looks brighter” — a fake step. Readers take that fake step as “the data changes abruptly here” — the figure manufactures structure that does not exist in the data, which is far more serious than “looking bad”.

Teaching point: reading the theory is no substitute for getting it wrong once yourself. This section's demo deliberately lets you switch among three wrong options, and each time it tells you “what is wrong” — seeing red and green blur together under deuteranopia simulation with your own eyes sticks better than reading the rules a hundred times.

3 ⭐ Key code
① Wrong example: a rainbow scale (deliberately wrong) 
// ⚠ this deliberately uses a rainbow scale, precisely to demonstrate a mismatch:
//   the hue sweeps through 0→320°, producing a "rainbow Jet"-style scale.
//   Its defect is not ugliness but non-uniform perception — it invents a fake bright step where the data is flat.

3.7 The vivid + low-saturation philosophy generator

Fewer than 7 colors, vivid hues + low saturation — good looking, and it wears well.

1 Your original case

You want to give each of the five regions in crime.csv a color, and you want the whole figure to look “designed”. Turning saturation all the way up (S=100%) glares, and turning everything down goes grey — hence this chapter's set of rules of thumb:

RuleParameterWhy
Keep the count smallColors ≤ 7Beyond 7 the eye can no longer separate neighboring categories
Pull the hues apartHue difference between neighbors ≥ 30°Use hue to open up the “inter-class distance” so categories pop
Push saturation downSupporting colors S = 30–50%No single color should be too “loud”, so the whole page wears well
Keep the primary slightly vividPrimary S = 70–80%Distinct but not glaring; it carries the “lead role”
Keep highlights very paleHighlight L = 85–90%For backgrounds, annotations, reference lines
2 Embedded theory

The 7-color generation rule: a recipe of “one primary + two neighbors + one opposite + one highlight level”

Primary + 2 analogous (±30°) + 1 analogous low-saturation + 1 complementary + 1 complementary low-saturation + 1 highlight = 7 colors. It satisfies “≤ 7” and “hues at least 30° apart” at the same time, while the low-saturation levels are what “hold the whole page down” and make the primary stand out more.

Why split primary / supporting colors: in one figure only one or two series really need to “pop”, and the rest are supporting parts. Making every color vivid is the same as having no emphasis; making every color low-saturation is also the same as having no emphasis — a clear hierarchy is what looks good.

3 ⭐ Key code
① The 7-color generation rule 
// input base hue H, primary saturation S, primary lightness L; output 7 colors (S / L are adjusted by level)
function genPalette(H, S, L) {
  const rotate = (d) => (H + d + 360) % 360;   // safe circular hue
  const s = (k) => Math.max(0, Math.min(100, S * k));
  const l = (k) => Math.max(0, Math.min(100, L * k));
  return [
    hsl2rgb(rotate(-30), s(0.6), l(1.10)),   // analogous 1 · low saturation
    hsl2rgb(rotate(-30), s(1.0), l(1.00)),   // analogous 1
    hsl2rgb(H,            s(1.0), l(1.00)),   // primary ★
    hsl2rgb(rotate(30),  s(1.0), l(1.00)),   // analogous 2
    hsl2rgb(rotate(30),  s(0.6), l(1.10)),   // analogous 2 · low saturation
    hsl2rgb(rotate(180), s(0.8), l(0.95)),   // complementary · accent
    hsl2rgb(H,            s(0.2), l(1.40)),   // highlight (very low saturation)
  ];
}

In the recipe every color is determined by a triple of (hue offset, saturation factor, lightness factor) — change these three coefficients and you can recolor the whole batch. Note rotate(): hue is circular, so an offset must be taken mod 360, otherwise you get negative angles or values above 360.

② HSL → RGB and the hex output 
// standard HSL → RGB (s, l are percentages)
function hsl2rgb(h, s, l) {
  s /= 100; l /= 100;
  const k = (n) => (n + h / 30) % 12;
  const a = s * Math.min(l, 1 - l);
  const f = (n) => l - a * Math.max(-1, Math.min(k(n) - 3, Math.min(9 - k(n), 1)));
  return [f(0) * 255, f(8) * 255, f(4) * 255].map((v) => Math.round(v));
}

// for "copy hex": convert to #rrggbb text
const hexOf = ([r, g, b]) =>
  '#' + [r, g, b].map((v) => v.toString(16).padStart(2, '0')).join('');

The hex shown on the demo page is there to be copyable and deliverable: the colors eventually go into someone else's paper or another chart. Note, though, that once a hex is hard-coded it loses the ability to adapt to the theme — so the body text and figures on this site still use tokens, and hex is only an “export result”.

③ “Copy all hex”: clipboard + fallback on failure 
async function copyAll(hexes) {
  const text = hexes.join(', ');
  try {
    await navigator.clipboard.writeText(text);       // first choice: the async clipboard API
    return '7 hex values copied';
  } catch (err) {
    // fallback 1: in a non-secure context / without permission, use a temporary textarea + execCommand
    try {
      const ta = document.createElement('textarea');
      ta.value = text; document.body.appendChild(ta); ta.select();
      const ok = document.execCommand('copy');
      ta.remove();
      if (ok) return 'copied (fallback mode)';
    } catch (e) { /* fall through to fallback 2 */ }
    showSelectable(text);                             // fallback 2: show a selectable text box
    return 'auto-copy was blocked by the browser; please select all and copy manually';
  }
}

navigator.clipboard is only available in a secure context (https or localhost); when you open the page locally over file:// it throws immediately. The three layers of protection (API → execCommand → selectable text box) guarantee that nothing ever “does nothing when clicked”, in any environment.

Self-check · 1 question

Under the “vivid + low-saturation” palette philosophy, what saturation range is recommended for the supporting colors of a scheme?

Supporting colors are the backing cast, so keep S at 30–50%: not so grey that the hue disappears, and not competing with the primary for attention. 70–80% is the level for the primary, and 90–100% glares — a page full of highly saturated colors means no emphasis at all.

3.8 CVD paper-figure test

Does your figure still make sense to a color-blind reader? Test it on the spot with real data.

1 Your original case

You submit a paper figure and the reviewer replies “figure 2 is hard to read”. You check the layout, font sizes, legend — all fine. Could it be that the reviewer has a color vision deficiency (CVD)? About 8% of men cannot distinguish the categories you encoded by color. First look at measured results for the three most common “paper figures” under CVD:

Paper figurePaletteMeasured CVD verdict
Fig. 1 · 5-class scatterWong 2011 / Okabe–Ito✅ distinguishable under all three simulations: protanopia / deuteranopia / tritanopia
Fig. 2 · sequential heatmapViridis / Cividis✅ lightness rises monotonically; still readable under CVD and grayscale printing
Fig. 3 · red/green two-color contrastred—green (wrong case)⚠ to a deuteranope the two are almost the same color — the most serious accessibility problem

The problem is not that the figure is “ugly” — it is that information disappears outright for part of your readers: in Fig. 3 the difference between the two categories is, to a color-blind reader, simply not encoded.

2 Embedded theory

The three CVD types and the “dual encoding” remedy

  • Protanopia: about 1% of men; the red photoreceptor is missing and the red—green axis collapses.
  • Deuteranopia: about 6% of men, the most common type; it likewise makes red—green hard to tell apart.
  • Tritanopia: extremely rare; the blue—yellow axis is affected.

Testing workflow: ① export the original figure as PNG → ② simulate the three CVD types with Coblis / Color Oracle → ③ check whether it is still distinguishable. Three criteria: is the lightness contrast still sufficient, are shapes / labels independent of color, and does each category still have a second, non-color encoding.

Redundant encoding is the universal remedy: stack a shape layer (circle / square / triangle / cross) on top of color, or label the categories directly. Then even if the colors collapse, shapes still separate the classes — grayscale printing benefits too.

3 ⭐ Key code
① CVD simulation: Machado 2009 approximation matrices 
// the three CVD types approximated by 3×3 linear transforms (fitted in the style of Machado et al. 2009)
const CVD_MATRICES = {
  protanopia:   [[0.567, 0.433, 0.000], [0.558, 0.442, 0.000], [0.000, 0.242, 0.758]],
  deuteranopia: [[0.625, 0.375, 0.000], [0.700, 0.300, 0.000], [0.000, 0.300, 0.700]],
  tritanopia:   [[0.950, 0.050, 0.000], [0.000, 0.433, 0.567], [0.000, 0.475, 0.525]],
};

// apply the matrix to one color, clamping the result to 0–255 (matrix row × input vector)
function simulateCVD([r, g, b], type) {
  const m = CVD_MATRICES[type];
  return m.map((row) =>
    Math.round(Math.max(0, Math.min(255, row[0] * r + row[1] * g + row[2] * b)))
  );
}

Each row of the matrix is “new channel = a weighted sum of the original three channels”. In the protan/deutan matrices the red and green rows are highly similar — that is the mathematical origin of “red–green collapse”: the deuteranopia rows [0.625, 0.375, 0] and [0.700, 0.300, 0] point in almost the same direction.

② Recolor a whole SVG in place (labels untouched) 
// walk every filled element and swap in simulated colors via the matrix; text / strokes stay untouched
function simulateSvg(svg, type) {
  svg.querySelectorAll('[fill]').forEach((el) => {
    if (!el.dataset.origFill) el.dataset.origFill = el.getAttribute('fill');   // back up the original color, restore when switching back to normal
    const rgb = parseCssColor(el.dataset.origFill);                    // handles both hex and rgb()
    el.setAttribute('fill', rgbStr(simulateCVD(rgb, type)));
  });
}
// switch back to “normal”: just write the backed-up originals back
svg.querySelectorAll('[data-orig-fill]').forEach((el) => el.setAttribute('fill', el.dataset.origFill));

The key is to change only fill, never stroke or text: if text is transformed too, the reader cannot tell “this is a simulated view” from “this is the real figure”. Backing up the original color (dataset.origFill) also turns “switch back to normal” into a single restore, avoiding error accumulation from repeated transforms.

③ Grayscale self-check: is lightness still separable 
// WCAG relative luminance: gamma-decode first, then weight by 0.2126 / 0.7152 / 0.0722
function luminance([r, g, b]) {
  const lin = (v) => {
    v /= 255;
    return v <= 0.03928 ? v / 12.92 : Math.pow((v + 0.055) / 1.055, 2.4);
  };
  return 0.2126 * lin(r) + 0.7152 * lin(g) + 0.0722 * lin(b);
}

// a lightness difference < 0.05 → the classes blur together in grayscale print; a second encoding is needed
const grayClash = (c1, c2) => Math.abs(luminance(c1) - luminance(c2)) < 0.05;

The grayscale self-check is CVD testing’s sibling: papers get printed in black and white, and if two classes differ only in hue — with equal lightness — they vanish in grayscale. The same luminance() also gives you the WCAG contrast ratio (see 3.4): two birds, one stone.

Theory lens · The first law of color: data type dictates scale type — ordered data (magnitude) takes a single-hue luminance ramp, diverging data (around a midpoint) takes a diverging two-end scale, and categorical data (unordered sets) takes a categorical palette (distinct hues, similar lightness). The four patients are four classic diseases: rainbow scales have no perceptual order in hue; the red–green pair is hazardous for color-vision deficiency (about 8% of men are red-green weak, and under deuteranopia the two colors nearly merge); two lines with near-equal lightness defeat the color channel; a gradient applied to unordered categories fabricates order out of thin air. Each cure follows the same logic: monotone luminance for order, blue–orange instead of red–green, lightness separation for legibility, and the Okabe–Ito safe palette for categories. One universal rule: never rely on hue alone — add shape, labels or line style as redundant encoding.

Self-check · 1 question

A figure that distinguishes two classes by red / green fails its CVD test: “to a deuteranope the two classes are nearly the same color”. The most effective remedy is?

The remedy must solve both problems at once: replace the collapsing palette (e.g. Wong / Okabe–Ito) and give each class an encoding independent of color (shape / annotation). Adjusting lightness alone is usually not enough (the hues stay close), and enlarging the legend or adding a note is worse — “knowing it is red–green doesn’t help”, because readers simply cannot tell which one is red and which is green.

4.1 Data Reshaping

Wide format is for people, long format is for programs — one flatMap completes the conversion.

1 Your Original Case

From start to finish this chapter uses a single dataset: crime.csv, 1985 crime statistics for the 50 US states. It holds 50 rows × 12 columns, one row per state and one metric per column — a classic wide format.

crime.csv field list: 1 identifier column + 1 population column + 10 crime-metric columns
ColumnMeaningType
stateState name (unique key)String
population1985 populationNumber (530k ~ 27M, spanning 50×)
population_growthPopulation growth rate (%)Number (can be positive or negative)
robbery / aggravated_assaultRobbery / aggravated assaultNumber (case count)
burglary / larceny_theft / motor_vehicle_theftBurglary / larceny theft / motor-vehicle theftNumber (case count)
murder / arson / rape1 / rape2Murder / arson / two rape definitionsNumber (case count)
2 Embedded Theory

Wide format vs long format

Wide format: one row per entity (state), with metrics as columns (murder, robbery…). It is easy for people to read at a glance, but the information "which metric" hides in the column names, where a program cannot reach it.

Long format: one row per observation, with fixed columns {state, metric, value}. The "metric" is demoted to a single data column, so filter / group / data-join can all split on it directly.

Conversion: for each state, walk the list of metrics to keep and expand the (state, metric, value) triple — that is flatMap. This is ES2019 syntax, equivalent to map() followed by flat().

How to choose: tables meant for people to read or fill in use the wide format; intermediate data meant for programs and D3 joins uses the long format. The same data usually "enters and leaves the pipeline in one format each", and the switch happens right on the flatMap line.

3 ⭐ Key Code
① d3.autoType: type inference as you load 
// Pass d3.autoType as the second argument to skip a +d.field per column
const raw = await d3.csv('./data/crime.csv', d3.autoType);

// Confirm the types really were converted:
console.log(raw[0].population);        // 3979000 (a Number, not "3979000")
console.log(typeof raw[0].state);      // "string"

Internally, autoType walks every column and tries Number() / Date() / boolean literals: whatever it can recognise it converts, and whatever it cannot it leaves as a string. So it is convenient but also conservative — a thousands-separated number like "1,234" is not converted for you and still needs its own cleaning.

② flatMap: the one-liner that goes wide → long 
// Wide format: one row per state, columns = metrics
// Long format: one row per observation {state, metric, value}
const METRICS = ['murder', 'robbery', 'burglary'];

const long = raw.flatMap(d =>
  METRICS.map(metric => ({
    state: d.state,
    metric,
    value: d[metric],
  }))
);
// 50 rows × 3 metrics = 150 rows
const byMetric = d3.group(long, d => d.metric);   // grouping, filtering, joining all just work

flatMap = "map, then flatten the result one level". Writing map(...).flat() gives the same result, but flatMap states the intent more clearly and avoids the intermediate nested array. Note: the row count rises from 50 to 150 — long format trades rows for operability.

③ Per-axis normalization before parallel coordinates 
// Parallel coordinates: min-max every axis independently into [0, 1]
const norm = (values) => {
  const lo = Math.min(...values), hi = Math.max(...values);
  const span = hi - lo || 1;          // avoid divide-by-zero when all values are equal
  return (v) => (v - lo) / span;
};
const yOfMurder = norm(raw.map(d => d.murder));

The biggest trap of parallel coordinates: each axis has a different scale. After normalization, comparing across axes compares "relative position", not absolute values — so you may say "this state sits high on the murder axis and low on the theft axis", but not "murder 350 = theft 350". Scatterplot matrices do not have this problem: for pairwise comparison both axes keep their real scales.

4 Runnable Demo

First use parallel coordinates to see the "profile" of the 50 states across 5 metrics, then use a scatterplot matrix for pairwise comparison. Pick an axis and drag the two sliders to brush — the selected states light up in sync across both charts; that is linked brushing.

Section Summary

  • Wide format: one row per entity (human-friendly); long format: one row per observation (program-friendly); flatMap does wide → long in a single line.
  • d3.autoType infers column types at load time, but it only makes conversions it can "guess", so dirty data still needs cleaning.
  • Parallel coordinates need per-axis normalization (across axes you read only relative position); scatterplot matrices compare with real scales — two different strategies for projecting multivariate data.
Self-check · Question 1

In crime.csv, "one row per state with one crime metric per column" — which layout is this?

Wide format = one row per entity (state), with columns as metrics (murder, robbery…). Only recasting it as one (state, metric, value) triple per row makes it long format — the shape that filter / group / data-join needs.

Self-check · Question 2

Taking the 50-row wide crime.csv and flatMap-ing it into long format with the three metrics ['murder', 'robbery', 'burglary'], how many rows do you get?

Each state expands into 3 observation rows: 50 × 3 = 150 rows. Long format trades rows for operability — the data grows bigger, but filter / group / binding joins all become simpler.

4.2 Coordinate Transforms

Data space → normalized space → screen-pixel space: three layers with clear duties; mix them up and everything falls apart.

1 Your Original Case

The original §5.1.2 uses a scatterplot to show murder vs robbery in crime.csv. The trouble: murders run from 32 (Vermont) to 3082 (California) and robberies from 489 (Wyoming) to 254707 (California) — if you feed the raw values directly as pixels, the canvas simply cannot hold them.

LayerCoordinate meaningValue in this caseWho owns it
① Data spaceRaw values (real units)murder = 3082Your data
② Normalized spaceStandardized coordinates squeezed into 0..innerWx' = 0.98scaleLinear / scaleLog / scaleSqrt
③ Screen-pixel spaceFinal pixel position after adding the margin offsetX = 48 + 0.98×560 ≈ 597 pxThe second-layer scale or d3.axisBottom
2 Embedded Theory

Why three layers are mandatory

Splitting "value → coordinate" from "coordinate → pixel" buys decoupling: the normalized result depends only on the data, while the screen pixel depends only on the canvas size. So resizing the canvas (responsive layout, exporting charts at different sizes) recomputes only the third layer, and the first layer's normalized result is reused as-is.

If you take the shortcut of "one scale that handles both domain=data and range=[margin, margin+innerW]", then every change to the margin forces you back into the data layer — and coordinates shared between elements (say the position of a reference line) can no longer be reused.

A common slip: writing "data domain → pixel domain" into a single scale (domain=[0, maxMurder], range=[margin, margin+innerW]). At the time nothing looks wrong, until you need to change the margin, go responsive, or overlay a shared reference line — and only then discover that every scale has to be edited in two places.

3 ⭐ Key Code
① Two scales: data → normalized → pixel 
const M = { t: 20, r: 20, b: 36, l: 48 };   // margins
const innerW = W - M.l - M.r, innerH = H - M.t - M.b;

// First layer: data space → normalized space (depends only on the data)
const xData = d3.scaleLinear().domain([0, maxMurder]).range([0, innerW]);

// Second layer: normalized space → screen-pixel space (depends only on the canvas)
const xScreen = d3.scaleLinear().domain([0, innerW]).range([M.l, M.l + innerW]);

// Compose them at render time: data → normalized → pixel
.attr('cx', d => xScreen(xData(d.murder)))

domain() is the input and range() the output. Once the two layers are separated, xData can be shared across many charts (the mini-charts of one dataset), while xScreen is used once at render time. Rule of thumb: the inner layer owns the data, the outer layer owns the canvas.

② Choosing the first-layer scale: linear / log / sqrt 
// Even distribution: the most common choice, a straight linear map
const xLin  = d3.scaleLinear().domain([0, maxMurder]).range([0, innerW]);

// Across orders of magnitude (population 530k ~ 27M): log turns equal ratios into equal distances
const xLog  = d3.scaleLog().domain([1, maxMurder]).range([0, innerW]);

// Area perception: map the squared radius to the value (the right way to do bubble charts)
const xSqrt = d3.scaleSqrt().domain([0, maxMurder]).range([0, innerW]);
// Categorical axes use scaleBand (bar charts); don't order categories with scaleLinear

Swapping the scale touches only the first layer; the second layer stays completely unchanged — that is the value of the split. The data distribution decides which first-layer scale to use: linear for even data, log across orders of magnitude, sqrt when mapping to area (not length).

4 Runnable Demo

Click "Next" to step through the layers and watch the same states change coordinates at each one; switching linear / log / sqrt above also changes the layer ② normalization, and the table on the right gives each point's three sets of coordinates plus the current formula.

Section Summary

  • Three duties: data space (real values) → normalized space (0..innerW) → screen-pixel space (plus margin); the bridge between layers is the scale.
  • The split buys decoupling: the normalized result is independent of canvas size, resizing recomputes only the outermost layer, and shared elements (reference lines, grids) need no recompute.
  • The first-layer scale follows the data distribution: linear for even data, log across orders of magnitude, sqrt for area, band for categories.
Self-check · 1 question

Splitting "data space → normalized space → screen-pixel space" into two scales mainly gives you what?

The second layer depends only on canvas size and the first only on the data. When you change the canvas, the first layer's normalized result is reused as-is — and shared elements (grid lines, reference lines, other mini-charts) all share the same set of coordinates. d3 does not force two layers.

4.3 Curve Fitting

For the same set of points, a different model is a different trend line — what tells you which one fits better?

1 Your Original Case

The original §5.1.3 shows the trend across 50 states with "polyline + points", and the code says curveCatmullRom — but never explains why, so the result is a curve that overfits and draws out every state's jitter.

2 Embedded Theory

Interpolation vs fitting

Interpolation: the curve passes through every data point (Catmull-Rom, Natural, monotoneX). It keeps all the information, but draws the noise in with it.

Fitting: the curve is not required to pass through the data points, it only reflects the trend (linear regression, power function, LOESS). It deliberately "throws away" the point-to-point detail in exchange for seeing the overall direction.

How to choose: few points (< 10) → interpolate, there isn't much information to waste anyway; many points (> 30) → fit, most of the jitter is noise; data that has an inherent order and must stay monotone → monotoneX (no spurious oscillation).

Don't forget the colormap. The colors used in this section's scatterplots also follow Chapter 3's rules: one hue per category, no rainbow ramp — color only distinguishes "selected or not", it does not encode a value.

3 ⭐ Key Code
① d3.line().curve(): swap one line to change the style 
const line = d3.line()
  .x(d => x(d.population))
  .y(d => y(d.murder))
  .curve(d3.curveMonotoneX);   // ← change only this line to switch curve style

svg.append('path')
  .datum(data)                 // hand the whole array to the path as a single datum
  .attr('d', line)
  .attr('fill', 'none');

datum() binds the array as a whole to one element (not element by element). Common curves: linear straight joins, monotoneX keeps monotonicity, catmullRom smooths through the points, step stairsteps. Rule of thumb: ordered data → monotoneX, heavy jitter → a smooth spline, discrete states → step.

② Least squares: linearize a power function to solve it 
// Power function y = a · x^b → take logs on both sides to get a line: ln y = ln a + b · ln x
const pts = data.filter(d => d.population > 0 && d.murder > 0);
const lx = pts.map(d => Math.log(d.population));
const ly = pts.map(d => Math.log(d.murder));

const { slope, intercept } = ols(lx, ly);   // simple linear regression
const a = Math.exp(intercept), b = slope;   // the two parameters of the power function

"Linearization" is the master key to fitting: exponential, power, inverse and square-root models can all be turned into a straight line by a change of variables, then fed to the same ols(). Note: minimizing error in the linearized space is not the same as minimizing it in the original space — so an R² computed after taking logs must be evaluated back in the original space.

③ R²: a common yardstick for goodness of fit 
// R² = 1 − SSres / SStot: the closer to 1, the better the fit
const mean  = ys.reduce((s, v) => s + v, 0) / ys.length;
const ssTot = ys.reduce((s, v) => s + (v - mean) ** 2, 0);
const ssRes = ys.reduce((s, v, i) => s + (v - fit[i]) ** 2, 0);
const r2 = 1 - ssRes / ssTot;   // can go negative: worse than "just use the mean"

R² is not "the higher the better". It measures the improvement over the mean baseline: a straight line reaching 0.6 over 50 states is already good, while a cubic polynomial can always squeeze out another 0.02 — but that 0.02 is usually just fitting the noise. When comparing R², look at the parameter count as well.

4 Runnable Demo

Use the buttons below to switch between 10 fitting models: the same paired points (population → murders) stay put while the curve, fitted equation and R² update together; the ranking bar on the right sorts by R² from high to low, showing at a glance which fits best.

Section Summary

  • Interpolation passes all points (keeps information and noise); fitting only reflects the trend (drops detail, sees clearly); the point count is the main criterion.
  • d3.line().curve() changes style in one line: ordered data → monotoneX, heavy jitter → a smooth spline, discrete states → step.
  • Fitting unifies everything under least squares via "linearization"; when comparing goodness with R² you must also weigh model complexity, or you'll pick the overfitted one.
Self-check · Question 1

For a line chart with only 8 data points, which curve keeps the sequence monotone without spurious oscillation?

Tension splines like Catmull-Rom can "flick" a bump between points that isn't really there (spurious oscillation). monotoneX constrains each segment's cubic term so that "if the data rises, it doesn't bend down" — the safest default for time series and ordered data.

Self-check · Question 2

About goodness of fit R², which statement is correct?

R² = 1 − SSres/SStot, with the baseline being "predict everything with the mean". It can be negative (worse than the mean, meaning the model is entirely unsuitable); it is only comparable within the same dataset and meaningless across datasets; and the higher the complexity the more easily it is inflated — so look at the parameter count (or adjusted R²).

4.4 Slope Perception (the 45° golden angle)

The eye's estimate of slope is not linear — 45° is the visual "midpoint".

1 Your Original Case

The original §5.1.4 mentions "the optimal average inclination is 45°" but never explains why. And for data spanning 50× like crime.csv, drawn on a linear axis, most states clump together and the trend line's slope is nearly horizontal (< 20°), so readers can barely read the slope.

2 Embedded Theory

Cleveland's 1984 slope-estimation experiment

Participants estimated the slope of straight lines and reported the deviation of their perceived value from the true value; the result is a U-shaped curve:

  • When the slope approaches 0° or 90°, estimation error is largest (it is nearly impossible to judge "whether this difference counts as steeper").
  • When the slope approaches 45°, estimation is most accurate — this is the "golden angle".

Stevens's power law explains why: perceived slope ≈ true slope1.0~1.3, i.e. the eye exaggerates steepness by about 30% overall. Only near 45° do the "exaggeration" and "compression" errors cancel, so perception comes closest to reality.

Design principles: ① keep the key data's slopes within 30°–60°; ② when comparing growth curves, use a log axis to pull the steepness back toward about 45°; ③ avoid trend comparisons below 5° or above 85° — there the perceptual error is enough to lead you to a wrong conclusion.

3 ⭐ Key Code
① Angle → screen coordinates (mind SVG's downward y-axis) 
// SVG's y-axis points down (the opposite of math coordinates), so the sin term is negated
function lineAt(deg, len = 240, o = { x: 100, y: 240 }) {
  const r = deg * Math.PI / 180;
  return {
    x1: o.x, y1: o.y,
    x2: o.x + len * Math.cos(r),
    y2: o.y - len * Math.sin(r),
  };
}

This is the first trap when drawing angle figures: SVG has its origin at the top-left and y growing downward, so the sin term must be negated, otherwise 30° is drawn as "30° down to the right". The second trap: angles must be converted to radians before being fed to Math.cos / Math.sin.

② The U-shaped error model + slider driving 
// Cleveland's U-shaped error: |ln(tan θ)| is 0 at 45° and diverges toward the ends
const err = (deg) => {
  if (deg <= 0 || deg >= 90) return 1;
  const r = deg * Math.PI / 180;
  return 1 - Math.exp(-Math.abs(Math.log(Math.tan(r))));
};

slider.addEventListener('input', e => draw(+e.target.value));

Turning abstract theory into an adjustable parameter is what lets students "feel" it: dragging the slider updates both the "line's inclination" and the "cursor on the error curve", and once the two pieces of information correspond, the meaning of the U shape sticks.

③ Using a log axis to pull the trend slope back to 45° 
// Exponential growth on a linear axis is "slow then steep": slope 5° → 85°, distorted at both ends
// Switch to a log axis: equal ratios become equal distances, and the trend's inclination falls back near 45°
const xLog = d3.scaleLog()
  .domain(d3.extent(data, d => d.population))   // [530k, 27M]
  .range([0, innerW]);

// Check: regress the points onto a "normalized square canvas" and measure whether the angle entered 30°–60°
const angle = Math.atan(ols(normX, normY).slope) * 180 / Math.PI;

This is where 4.2's scale selection connects with this section's design principles: swapping the first-layer scale changes the inclination of that trend line on screen. In the demo below, switching linear / log shows the angle computed from the very same regression coefficient jumping from < 20° into the golden range.

Section Summary

  • Cleveland 1984: slope-estimation error is U-shaped, worst at 0° / 90° and best at 45°; take 30°–60° as the stable range.
  • Stevens's power law (perceived ≈ true1.0~1.3) explains why: the eye exaggerates steepness by about 30%, and near 45° that is exactly cancelled.
  • Design actions: herd the key slopes into 30°–60°; compress steepness on growth curves with a log axis — swapping the scale swaps the inclination.
Self-check · 1 question

Dragging the visual inclination from 45° to 85° with the slider, how does Cleveland's U-shaped error curve change?

Both sides of the U shape rise monotonically: starting from 45°, whether you move toward 0° or toward 90°, the error grows. Both 85° and 5° are in the "danger zone"; comparing trends at such inclinations lets perceptual error directly swamp the real difference.

4.5 Contours (Marching Squares)

Given a scalar field and a threshold, trace out the curve where "value = threshold".

1 Your Original Case

The original §5.2.2 extracts contours from crime.csv with Marching Squares, but the original code is a screenshot placeholder — in this lesson we complete it into a genuinely runnable algorithm and lay out every step.

The idea: first treat two metrics of the 50 states (say murder and robbery) as points on a 2D plane, use kernel density estimation (KDE) to lay out a scalar field, then take contours of this continuous field — what the contours enclose are regions of "similar density".

2 Embedded Theory

The idea: use "which corners of a cell are above the threshold" to decide how the segment runs

Discretize the scalar field into a grid. For each cell, look at whether its 4 corners exceed the threshold — the 4 booleans form a case number 0~15 (2⁴ = 16). Each case maps to 0 / 1 / 2 segments, which exactly separate the "above threshold" and "below threshold" regions.

Bit encoding: bit0 = BL, bit1 = BR, bit2 = TR, bit3 = TL (bottom-left → bottom-right → top-right → top-left, clockwise).

Each segment's endpoints lie on the cell's edges, positioned by linear interpolation: t = (threshold − a) / (b − a), where a and b are the values at the two grid nodes of that edge.

The only case that needs thought: case 5 and case 10 are saddle points (the two diagonal corners exceed the threshold), where the segment has two possible connections and the cell's center value is needed to decide which way to connect.

Generalizing to 3D: each cube has 8 corners → 2⁸ = 256 cases, which is Marching Cubes (Lorensen & Cline 1987), the standard for isosurface extraction in medical MRI / CT.

3 ⭐ Key Code
① EDGE_TABLE: the core data structure for the 16 cases 
// Edge numbering: 0 = left-middle, 1 = bottom-middle, 2 = right-middle, 3 = top-middle
const EDGE_TABLE = [
  [],                  // 0000 all below threshold → no segment
  [[3, 0]],            // 0001 only BL above
  [[0, 1]],            // 0010 only BR above
  [[3, 1]],            // 0011 BL + BR
  [[1, 2]],            // 0100 only TR above
  [[3, 0], [1, 2]],    // 0101 saddle (check the cell center)
  [[0, 2]],            // 0110 BR + TR
  [[3, 2]],            // 0111 only TL below
  [[2, 3]],            // 1000 only TL above
  [[2, 0]],            // 1001 TL + BL
  [[0, 1], [2, 3]],    // 1010 saddle (check the cell center)
  [[2, 1]],            // 1011 only BR below
  [[1, 3]],            // 1100 TR + TL
  [[1, 0]],            // 1101 only TR below
  [[0, 3]],            // 1110 only BL below
  [],                  // 1111 all above threshold
];

This table is the whole algorithmic logic of Marching Squares — everything else is table lookup plus interpolation. Cases 0 and 15 have no crossing (the whole cell is on one side), while cases 5 and 10 each have 2 segments and an ambiguous direction.

② Assembling the case number with bitwise ops 
// Whether each of the 4 corners exceeds the threshold → 4 bits → case number 0~15
let code = 0;
if (bl > threshold) code |= 1;   // bit 0
if (br > threshold) code |= 2;   // bit 1
if (tr > threshold) code |= 4;   // bit 2
if (tl > threshold) code |= 8;   // bit 3

const segs = EDGE_TABLE[code];    // table lookup gives 0 / 1 / 2 segments

Using |= to accumulate "powers of two" is the classic bitwise idiom: four booleans assemble exactly into a number 0~15. The order matters — the 0/1/2/3 edge numbering in the table must correspond one-to-one with the bit arrangement here, or segments will connect at the wrong places.

③ Linear interpolation on edges for crossing points (with saddle direction) 
// Position t ∈ [0,1] of the level point on edge (a→b)
const t = (threshold - a) / (b - a);
const px = ax + t * (bx - ax);
const py = ay + t * (by - ay);

// Saddle: compare the cell center with the threshold to decide which pair of edges each segment connects
const center = (tl + tr + bl + br) / 4;
// code 5: center > threshold → connect [3,0]; otherwise [1,2]
// code 10: center > threshold → connect [2,3]; otherwise [0,1]

Why interpolation is mandatory: if you take the lazy route of the edge midpoint, the contour becomes a jagged polyline that gets uglier the coarser the grid. Linear interpolation slides the crossing point along the edge in proportion to the values, giving a smooth curve even on a coarse grid.

4 Runnable Demo

Click "Next" to walk through the algorithm step by step: sample the grid → mark cells above the threshold → interpolate crossing points on edges → connect into polylines; you can also "Play" to run it automatically, and drag the threshold slider to watch the contour deform — sometimes splitting into two loops.

Section Summary

  • Marching Squares = using each cell's "whether its four corners exceed the threshold" to assemble a case number (0~15), then a table lookup gives 0/1/2 segments that separate the two regions.
  • Segment endpoints come from linear interpolation on the edges (t = (threshold − a)/(b − a)), which is the key to smooth contours.
  • Only the saddle (case 5 / 10) is ambiguous and needs the cell-center value to decide direction; generalized to 3D it becomes Marching Cubes with 2⁸ = 256 cases.
Self-check · 1 question

In Marching Squares, why do cases 5 and 10 need special handling?

Only all-above (15) and all-below (0) have no segments. Cases 5 / 10 have two diagonal corners above the threshold, so the two segments can either "enclose the two big corners" or "enclose the two small corners" — geometrically ambiguous; the algorithmic convention is to compare the cell-center value with the threshold to settle it.

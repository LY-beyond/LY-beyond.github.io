8.1 The Five position Values

Whether an element leaves the document flow is up to this

The Flex and Grid we met earlier all work inside "normal flow". position offers a different ability: lifting an element out of normal flow and putting it wherever you like.

ValueReference pointLeaves the flow?Typical use
staticnone (default)NoOrdinary elements
relativeits own original positionNo (the original position is kept)Nudging a position / acting as the parent for absolute
absolutethe nearest positioned ancestorYesBadges, dropdowns, overlays
fixedthe browser viewportYesBack-to-top buttons, floating bars
stickythe nearest scrolling containerNo (it sticks once it crosses the threshold)Sticky nav, sticky table headers

⭐ Key point: "absolute child, relative parent" is the most useful mnemonic in positioning — set position: relative on the parent and position: absolute on the child, and the child positions itself relative to the parent instead of flying off across the page. Forgetting to position the parent is the trap beginners fall into most often.

👉 See it in the case

The sticky nav uses position: sticky, not fixed — 9.3 Top nav bar. Lab step 3 checks position and top.

/* Absolute child, relative parent: the classic pairing */
.card {
  position: relative;   /* parent: provides the positioning reference */
}
.badge {
  position: absolute;   /* child: leaves the document flow */
  top: 8px;
  right: 8px;
}

/* Sticky navigation */
.navbar { position: sticky; top: 0; }

⭐ Key point: the reference point for absolute is "the nearest ancestor whose position is not static"; if it finds none all the way up, it positions against the initial containing block (roughly the top-left corner of the page).
Note: fixed is unaffected by ancestors — it is always relative to the viewport.

Switch the position value and watch the relationship between the red dashed box (the original position) and where the element actually ends up.

8.2 Offsets

How top / right / bottom / left are actually resolved

Once an element has a position other than static, you can "push" it around with the four properties top / right / bottom / left.

📐 Two rules

1. The reference point decides the meaning: the very same top: 20px means "move 20px down from its own original position" under relative, but "20px from the top of the parent container" under absolute.
2. Giving both left and right (or top and bottom) stretches it: if both left and right are set and there is no fixed width, the element is stretched to fill.

  • Values can be lengths (20px) or percentages (relative to the parent's size).
  • Negative values work too, e.g. top: -10px pushes the element in the opposite direction.
  • Setting these four properties on a static element has no effect at all.

⭐ Key point: when top and bottom are both present they "tug" against each other, and the stretching effect only shows up when the element's height is auto; if the element already has a fixed height, top wins. When debugging a positioning problem, first confirm "what is the reference point".

👉 See it in the case

In the case top: 0 is the offset that means “stick to the top of the viewport” — 9.3 Top nav bar.

/* relative: offsets from its own original position */
.shift { position: relative; top: 12px; left: 24px; }

/* absolute: relative to the positioned parent container */
.tip { position: absolute; bottom: 100%; left: 0; }

/* writing both left and right -> stretches to fill (when there is no fixed width) */
.full { position: absolute; left: 0; right: 0; }

⭐ Key point: bottom: 100% is often used for "tooltip bubbles" — it means "move to above the top of the parent", i.e. sitting entirely outside the parent's top edge, so you never have to work out the bubble's height by hand.

Drag the top / left sliders and observe how the positioning reference point differs between relative and absolute.

8.3 z-index and Stacking

Who is on top, and who is underneath

When elements overlap, the browser needs a rule to decide which one is painted on top — that is z-index (the z-axis coordinate).

🧱 Three preconditions

1. z-index only applies to positioned elements (position not static) or to flex / grid children;
2. the value may be negative, and a larger number covers a smaller one;
3. it creates a stacking context, and a child's z-index is only compared inside its own parent.

⭐ Key point: the usual reason "z-index doesn't work" is that you forgot to give the element a position — writing z-index: 9999 on a position: static element does absolutely nothing.
Another frequent cause is that the stacking context is locked by the parent: once the parent has transform / opacity < 1 and similar properties, no child z-index can escape the parent's level.

👉 See it in the case

The nav’s z-index: 50 keeps it above the content scrolling underneath — 9.3 Top nav bar.

.box-a { position: absolute; z-index: 1; }
.box-b { position: absolute; z-index: 2; }  /* b covers a */
.box-c { position: absolute; z-index: 3; }  /* c is on top */

/* To let a child escape the parent's stacking, first make sure the parent creates no stacking context */

⭐ Key point: the least painful habit in practice is not to scatter z-index values everywhere, but to set a small number of explicit levels only for the elements that need to float up (say 1 / 10 / 100 / 1000) and keep them in one place in the project, so you never end up with "9999 everywhere".

Drag the three z-index sliders and watch how the stacking order of the overlapping boxes changes.

8.4 Viewport and Media Queries

Let CSS make the decisions based on screen width

The first step of responsive design is telling the browser "render at the device's real width" — and that takes one meta tag:

<meta name="viewport" content="width=device-width, initial-scale=1.0">

With that in place you can use a media query to apply different styles at specific widths:

📱 Common breakpoints

< 640px phone　·　640–1024px tablet　·　> 1024px desktop

⭐ Key point: forgetting the viewport meta tag is the number one cause of "mobile looking like a shrunken desktop page" — iOS / Android render at 980px wide by default and then scale the whole thing down. Add this one line and media queries start using the real logical width.

👉 See it in the case

The case uses exactly two breakpoints: 760px (two columns) and 1040px (more whitespace) — 9.8 Responsive & self-check.

/* Desktop styles (default) */
.cards { display: grid; grid-template-columns: repeat(3, 1fr); }

/* Switch to a single column when the screen is <= 700px */
@media (max-width: 700px) {
  .cards { grid-template-columns: 1fr; }
}

⭐ Key point: max-width means "applies when the width is no more than this", and min-width means "applies when the width is at least this". You can mix the two, but it is recommended to standardise on min-width (mobile first) because the logic is clearer.

Drag the "screen width" slider and watch the layout inside the simulated viewport switch at the breakpoints.

8.5 Mobile First

Write from small to large, not the other way around

There are two routes for writing responsive CSS. The result is identical, but the maintenance cost differs enormously:

RouteDefault stylesMedia queries useMaintenance feel
Mobile first (recommended)Phone: single columnmin-width, progressively enhancedKeeps "adding" as you go — clear
Desktop firstDesktop: multi-columnmax-width, progressively overriddenTurns into "patching" — conflict-prone

⭐ Key point: the essence of mobile first is "make the small screen work first, then add for the bigger ones". Because phones have the worst performance and bandwidth, writing the small-screen styles first means they only load the rules they need, and it avoids the chore of "desktop styles are too full, so override them one by one on small screens".
Practical advice: order the min-width media queries from small to large, and in each breakpoint write only "what is newly added compared to the step before".

👉 See it in the case

The case’s last step refactors desktop-first into mobile-first: a single column by default, enhanced with min-width — 9.8 Responsive & self-check. Lab step 8 verifies 375 = one column, 1180 = two.

/* 1. Default = mobile: a single column */
.cards { display: grid; gap: 16px; }

/* 2. Tablet and up: two columns */
@media (min-width: 640px) {
  .cards { grid-template-columns: repeat(2, 1fr); }
}

/* 3. Desktop and up: three columns */
@media (min-width: 1024px) {
  .cards { grid-template-columns: repeat(3, 1fr); }
}

⭐ Key point: note that each media query only changes the column count and does not repeat display: grid and gap — those are inherited from the mobile default. That is exactly what "progressive enhancement" means.

Switch between the two approaches and compare how the CSS is organised for the same visual result.

8.6 Relative Units

Beyond px there are "smarter" lengths

Responsiveness is not only about media queries — relative units let sizes "follow the environment" automatically, and often let you skip breakpoints entirely.

UnitRelative toTypical use
pxabsolute pixelsFixed details such as borders and shadows
remthe root (html) font sizeFont sizes and spacing — most recommended
emthe current element's font sizeProportional scaling inside a component
%the corresponding size of the parentWidth and height proportions
vw / vh1% of the viewport width / heightFull-screen blocks, oversized headings

⭐ Key point: rem only works because the root font size can be adjusted by the user — the browser default for html is 16px, so 1rem = 16px. The advantage of sizing type in rem is that when a user changes their browser's font size setting, the whole page scales up proportionally, whereas px does not — an important part of accessibility (a11y).

👉 See it in the case

Two places use relative units in the case: the hero’s clamp(30px, 4vw, 46px) and the container’s min(100% - 48px, 1180px) — 9.4 Hero.

/* 1rem = the root font size (16px by default) */
.title { font-size: 2rem; }      /* = 32px */
.gap-lg { margin: 1.5rem 0; }  /* = 24px */

/* Type scales smoothly with the viewport — no breakpoint needed */
h1 { font-size: clamp(28px, 5vw, 48px); }

/* A block that is at least one screen tall */
.hero { min-height: 100vh; }

⭐ Key point: clamp(minimum, ideal, maximum) is the "magic tool" for responsive type — it lets the font size grow smoothly as the viewport widens, without becoming unreadably small or absurdly large. This site's headings use exactly that.

Adjust "root font size" and "viewport width" and observe how differently rem / em / % / vw resolve from the same number.

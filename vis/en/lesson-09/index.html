9.1 Planning the Case Study and the Wireframe

Settle the goal and the structure first, then start writing code

From this section on we are going to build a complete "personal portfolio website". The whole process takes 8 steps, and every step uses design principles and techniques from the chapters you have already read.

🎯 Case requirements (Ch. 2: ask about the goal first)

Page goal: let a visitor understand "who I am and what I can do" within 10 seconds, and want to get in touch.
Target audience: recruiters and collaborators.
Success criterion: the visitor clicks "contact me" after browsing the portfolio.

Content inventory and priority

SectionPriorityRationale (Ch. 1: contrast and hierarchy)
Hero — one-line intro + avatar★★★The first screen decides whether the visitor stays
Portfolio★★★Proves ability; the core persuasive material
About me★★Background that builds trust
Statistics★★Numbers reinforce credibility
Contact★★The conversion entry point

⭐ Key point: note that we first write down "what the page should make the user do", then work backwards to the sections — the order is "goal → content → structure → visuals → code", rather than opening an editor and starting to type.
Visual flow (Ch. 2): the Hero sits top-left (the first glance), the portfolio in the middle (the body), and contact at the bottom (the Z-pattern end point) — which matches how a visitor actually reads. 

<!-- Wireframe stage: sketch the skeleton with semantic sections first -->
<body>
  <header class="site-header"> ... </header>   /* navigation */
  <section class="hero"> ... </section>         /* first screen */
  <section class="about"> ... </section>        /* about me */
  <section class="works"> ... </section>        /* portfolio */
  <section class="stats"> ... </section>        /* statistics */
  <footer class="site-footer"> ... </footer>   /* contact + footer */
</body>

⭐ Key point: at this stage you write only the structure and class names, and no styles at all. Using semantic tags such as <header> / <section> / <footer> helps accessibility and makes the "skeleton" obvious at a glance.

Switch between the wireframe and the "content filled in" view, and watch the skeleton stay put while content is filled in step by step.

9.2 Page Skeleton and Grid

Give the whole site one shared ruler

The skeleton is in place; next we give the page a ruler — and this step decides whether every section that follows can line up.

📐 Three things (Ch. 3: grid systems)

1. Container: maximum content width 1180px, whitespace on both sides, horizontally centered.
2. Grid: 12 columns, 24px gutters.
3. Spacing scale: 8pt steps (8 / 16 / 24 / 40).

⭐ Key point: define the container and the grid once, then reuse them site-wide — the 6 sections that follow all use .container and .grid directly, so their left and right edges line up by construction (Ch. 1: alignment).
Why 1180px? It is a common rule of thumb: on screens of 1366px and above it leaves roughly 90px of breathing room on each side, and a single line of text stays inside the comfortable reading range (about 75 characters). 

/* 1. Container: cap the content width and center it */
.container {
  width: min(100% - 48px, 1180px);
  margin-inline: auto;
}

/* 2. 12-column grid: shared site-wide */
.grid {
  display: grid;
  grid-template-columns: repeat(12, 1fr);
  gap: var(--space-lg);
}

/* 3. Spacing steps (kept in tokens.css) */
:root {
  --space-sm: 8px;
  --space:    16px;
  --space-lg: 24px;
  --space-xl: 40px;
}

⭐ Key point: width: min(100% - 48px, 1180px) is a one-line way of saying "24px margin on small screens, at most 1180px on large ones" — tidier than writing max-width plus a media query.

Adjust the container width and the gutter and watch whether the 6 sections stay aligned to the same set of column lines.

9.3 The Top Navigation Bar

The site's first "alignment demonstration"

The nav bar is the simplest section, yet it concentrates three principles.

🧭 Design decisions for the nav bar

Layout: Flex + justify-content: space-between (Ch. 6) — it pushes the logo and the menu to opposite ends.
Alignment: align-items: center keeps the text vertically centered (Ch. 1).
Proximity: gap pulls the menu items tight together while a large distance separates them from the logo, so "logo" and "menu" read as two clear groups (Ch. 1).

⭐ Key point: when the nav bar needs to stick to the top, use position: sticky (Ch. 8) rather than fixed — sticky keeps its original slot, so the content below does not jump up.
Common pitfall: a sticky element's parent must not have overflow: hidden, or it stops working (because the scrolling container has changed). 

.site-header {
  position: sticky;      /* sticks to the top, and keeps its slot */
  top: 0;
  z-index: 50;
  backdrop-filter: blur(10px);   /* frosted glass */
  border-bottom: 1px solid var(--c-border);
}

.site-header .inner {
  display: flex;                  /* Ch. 6 */
  align-items: center;
  justify-content: space-between;  /* logo ↔ menu at opposite ends */
  height: 60px;
}

.site-header nav {
  display: flex;
  gap: 6px;                  /* between menu items: tight */
}

⭐ Key point: with two children, justify-content: space-between reads as "one to the left, one to the right"; with more than two it pushes the first and last to the edges and distributes the rest evenly in between — understand that and you will not misuse it.

Change the number of menu items and the alignment, and watch how the nav bar distributes and groups them.

9.4 The Hero Section

The one screen that decides whether the visitor stays

The hero is the section with the greatest visual weight on the page, and the place where the design principles are densest.

🎨 Four principles at work in the hero

Hierarchy: main heading 40px+, subheading 16px, body text 14px — the steps are pulled apart (§1.3).
Whitespace: use the largest step, --space-xl, for the vertical padding so the core content "floats" out.
Balance: text on the left and the avatar on the right, balanced asymmetrically with 7fr 5fr (§1.6).
Flow: heading → subheading → button, top to bottom, which matches the Z-pattern starting point (Ch. 2).

⭐ Key point: a hero may only have one "protagonist".
· if the heading, the avatar and the button all compete for attention, the visitor does not know where to look;
· the right approach: make the heading the largest, weaken the other elements in turn, and finish with one high-contrast button.
The power of contrast comes from the "drop" — actively muting the secondary elements (desaturating them, turning them grey) works better than enlarging the protagonist. 

.hero {
  padding: var(--space-xl) 0;     /* loose: the core area gets the most whitespace */
}

.hero .grid {
  display: grid;
  grid-template-columns: 7fr 5fr;  /* asymmetric balance */
  gap: var(--space-xl);
  align-items: center;
}

.hero h1 {
  font-size: clamp(30px, 4vw, 46px);  /* hierarchy + responsive type */
  line-height: 1.2;
  margin-bottom: var(--space);      /* heading and subheading: tight */
}

.hero .lead {
  font-size: 17px;
  color: var(--c-text-soft);       /* muted, to set off the heading */
  margin-bottom: var(--space-lg);
}

.hero .cta {
  background: var(--c-primary);        /* the only high-contrast element */
  color: #fff;
  padding: 12px 24px;
  border-radius: 999px;
}

⭐ Key point: align-items: center centers the two columns vertically; but mind this — when the two columns have different content heights, centering usually looks better than top alignment, because the visual weight is easier to balance.

Adjust the heading size, the whitespace and the left/right ratio, and feel how "hierarchy" and "balance" change.

9.5 About Me (two columns)

Image and text side by side: the ratio matters more than an even split

"About me" is the classic image-plus-text two-column block: an avatar or name card on one side, a written introduction on the other.

📊 Why is it usually not 1:1?

A portrait or a photo is visual information, whereas text is reading information. In practice the usual split is 4:8 or 5:7 — give the text column more width, because too many characters on a single line significantly slows reading down.

⭐ Key point: do not use 1fr 1fr for an image-and-text two-column layout. An even split looks "fair", but it makes the lines too long or the image too large, and both sides end up uncomfortable.
Another trap: if the image comes first in the DOM but you want the text to be read first (friendlier to screen readers and SEO), you should reorder the DOM or use order — "it looks right to the eye" is not enough. 

.about .grid {
  display: grid;
  grid-template-columns: 4fr 8fr;   /* image 4 : text 8 */
  gap: var(--space-xl);
  align-items: start;          /* top aligned: a long text block is not dragged around by "centering" */
}

/* Small screens stack automatically (Ch. 8: responsive) */
@media (max-width: 760px) {
  .about .grid { grid-template-columns: 1fr; }
}

/* Keep "proximity" between paragraphs: tight inside a paragraph, loose between them */
.about p { margin-bottom: var(--space); line-height: 1.9; }

⭐ Key point: this uses align-items: start (top aligned) rather than the center used in the hero. The deciding factor is content length: short content next to an image balances better when centered; a long paragraph next to an image wants top alignment, otherwise the text drifts away from where the reader's eye starts.

Switch the image/text ratio and the alignment, and watch reading comfort and visual balance change.

9.6 The Portfolio Card Wall

The core section of the case study: several works on one screen

The portfolio is the persuasive core of the whole page. A card wall carries it: it shows several works at once and stays tidy by construction.

🧱 Principles at work in the card wall

Repetition: every card has exactly the same radius, padding and shadow (§1.4) — that is where the "matching set" feeling comes from.
Common region: the card background frames the content into one group (§1.5).
Alignment: auto-fit + minmax makes the cards the same width and height automatically (Ch. 3).
Proximity: inside a card (image / title / tags) the spacing is 8px (tight); between cards it is 24px (loose).

⭐ Key point: the classic structure inside a card is a vertical Flex plus margin-top: auto — it pushes the "view details" link to the bottom of the card, so the buttons stay aligned even when the cards have different heights.
Why are the cards the same height? Because Grid's default align-items: stretch stretches every card in a row to the height of the tallest one. That is not a coincidence; it is a Grid feature. 

/* 1. The wall: an adaptive column count, no media query needed */
.works .wall {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(260px, 1fr));
  gap: var(--space-lg);         /* between cards: loose */
}

/* 2. The card: a vertical Flex so the bottom link sits flush with the base */
.work-card {
  display: flex;
  flex-direction: column;
  padding: var(--space);
  background: var(--c-surface);
  border: 1px solid var(--c-border);
  border-radius: var(--radius);
}

.work-card .thumb {
  aspect-ratio: 16 / 10;        /* a uniform ratio, so the heights never vary */
  border-radius: 8px;
  margin-bottom: var(--space-sm);
}

.work-card .more { margin-top: auto; }   /* ★ pushed to the very bottom */

⭐ Key point: aspect-ratio: 16 / 10 is what keeps the thumbnails at a uniform ratio. Without it, image heights follow the original dimensions and the whole wall ends up "up and down".

Adjust the minimum card width and the gap, then switch the card count, and watch the alignment and breathing room of the whole wall.

9.7 The Statistics Section

Numbers reinforce credibility, and they also test your "information hierarchy"

This section has to hold several small metrics and one large chart at the same time — exactly the "dashboard grid" scenario from Chapter 4.

📈 How is the information hierarchy built?

The number: 24–32px bold, in the primary color — it is the most important part.
The unit / suffix: 14px regular — secondary.
The caption: 12px grey — supporting.
Together the three form a 3-step drop, so you can read "what this number is" at a glance.

⭐ Key point: a number and its caption must "stay together" (proximity) — use 4–6px of vertical spacing, never the same distance as to the next metric, otherwise readers cannot tell which caption belongs to which number.
The spanning idea: set the container to 4 columns, give each small metric 1 column, and let the large chart take a whole row with grid-column: span 4 (Ch. 4). 

.stats .grid {
  display: grid;
  grid-template-columns: repeat(4, 1fr);   /* baseline: 4 columns */
  gap: var(--space-lg);
}

.stat {
  display: flex;
  flex-direction: column;
  gap: 4px;                    /* number and caption: tight */
  padding: var(--space);
  background: var(--c-surface);
  border-radius: var(--radius);
}

.stat .num { font-size: 28px; font-weight: 700; color: var(--c-primary); }
.stat .lbl { font-size: 12px; color: var(--c-muted); }

/* The large chart takes the whole row */
.stats .chart { grid-column: span 4; min-height: 180px; }

/* On small screens drop to 2 columns; the span shrinks automatically */
@media (max-width: 760px) {
  .stats .grid  { grid-template-columns: repeat(2, 1fr); }
  .stats .chart { grid-column: span 2; }
}

⭐ Key point: on small screens, changing span 4 to span 2 is a single override and no other metric has to change at all — that is exactly the benefit of "using span instead of hard-coding 1 / 5" (Ch. 4).

Switch between the spanning schemes and watch the relationship between the information hierarchy and the large chart.

9.8 Responsive Design and Self-Check

Make the case study work on every screen, and give your work a health check

The last step: make the whole case study display properly on a phone too, and run a systematic self-check.

📱 How do you decide the breakpoints? (Ch. 8)

Not "by device" but "by content" — drag the browser narrower until the moment the layout starts to feel uncomfortable; that is your breakpoint.
This case study uses only two breakpoints: 760px (the two columns stack) and 1040px (the column count drops).

✅ Layout design self-check list

CheckRelated theory
Is every element aligned to the same line?Alignment (1.1)
Is related content closer together? (within < between)Proximity (1.2)
Is the most important content the most prominent? Is the type-size jump big enough?Contrast (1.3)
Do similar elements share the same radius / shadow / color?Repetition (1.4)
Is the grouping clear enough that it needs no text explanation?Gestalt (1.5)
Is the left/right visual weight balanced? Does the whitespace have rhythm?Balance and rhythm (1.6)
Does every spacing value come from the same scale?Spacing scale (3.2)
Can the content still be read comfortably at phone width?Responsive (Ch. 8)

⭐ Key point: once the layout is finished, walk through this list item by item — far more effective than "adjusting it a bit by feel".
The list itself is a condensed version of the first half of this course (the Design track) — you do not need to memorise every CSS property, but you should memorise this list. 

/* Mobile first: single column by default, then progressively enhanced (Ch. 8) */
.about .grid,
.hero .grid { grid-template-columns: 1fr; }        /* default: phone */

@media (min-width: 760px) {                      /* from tablet: two columns */
  .hero .grid  { grid-template-columns: 7fr 5fr; }
  .about .grid { grid-template-columns: 4fr 8fr; }
}

@media (min-width: 1040px) {                     /* from desktop: more whitespace */
  .hero { padding: calc(var(--space-xl) * 1.6) 0; }
}

⭐ Key point: note that the media queries here use min-width, and the default styles serve the phone only — this is the mobile first approach from Chapter 8. Across the whole case study the small-screen styles are never overridden even once; they are only ever "enhanced".

2.1 Start with Goals and Priority

Don't rush to open the editor — answer three questions first

Layout is fundamentally about arranging content in space according to how much it matters. So the first step is not CSS at all — it is working out what is primary and what is secondary.

❓ Three questions to answer before you start

1. What should the user do on this page? (one single goal, e.g. "enroll in the course")
2. What is the single most important thing? (it should be the largest and most prominent)
3. What is secondary information? (it comes later and is visually muted)

From content inventory to layout

  1. List it: write down everything the page will hold (headings, images, buttons, notes…)
  2. Rank it: score each item 1–3 stars; more stars means earlier placement and more space
  3. Group it: cluster related items together (this is Chapter 1's proximity)
  4. Order it: decide top-to-bottom order by "where the user's eye will travel"

⭐ Key point: nine times out of ten a layout problem is really a priority problem. If a page looks "messy" it is usually not a CSS bug — it is that every piece of content is fighting for attention. No priority means no order.

👉 See it in the case

The case starts by fixing the page goal, audience and success criteria, then works back to the blocks — 9.1 Case planning. The lab begins here too.

/* Map priority onto visual weight (and pin it with variables) */
:root {
  --w-primary:   700;   /* level 1: large type + bold + accent color */
  --w-secondary: 500;   /* level 2: normal */
  --w-tertiary:  400;   /* level 3: muted grey */
}

.card-title { font-size: 22px; font-weight: var(--w-primary); }
.card-desc  { font-size: 14px; color: var(--c-text-soft); }

⭐ Key point: translate "priority" into reusable visual steps (size / weight / color) instead of tuning each element by hand — that way the page keeps its order as you add content.

2.2 Reading Patterns and Eye Paths

How a user's eyes actually "travel" across your page

People do not read a web page word by word — they scan it. A large body of eye-tracking research has identified a few typical eye paths; knowing them lets you put the important content right on the route.

PatternPathSuits
F-patternSweep across the heading → sweep across again → then scan rapidly down the left sideText-heavy pages: articles, documentation, lists
Z-patternTop-left → top-right → bottom-left → bottom-right (diagonally)Visual landing pages, poster-style pages
Gutenberg diagramTop-left (primary optical area) → top-right → bottom-left → bottom-right (terminal area)Symmetrical pages, card-based layouts

⭐ Key point: put the most important content on the eye path —
· on an F-pattern page, keep key information as far left and as high as possible;
· on a Z-pattern page, place the call to action (CTA) at the end of the path (bottom-right);
· conversely, if you put the focal point outside the path, users may never see it at all.

👉 See it in the case

The case’s visual path runs hero top-left → work in the middle → contact at the bottom: 9.1 Case planning.

/* A Z-pattern landing page: use Grid to put the CTA at the end of the path */
.landing {
  display: grid;
  grid-template-columns: 1fr 1fr;
  grid-template-areas:
    "brand   nav"
    "hero    hero"
    "text    cta";   /* ← the CTA lands bottom-right, matching the Z end point */
}

⭐ Key point: this is where Chapter 4's layout patterns meet this chapter — the eye path decides what goes where, and Grid / Flex then builds it.

2.3 Wireframes: Skeleton Before Skin

Lock the structure down with grey blocks, then talk about color and copy

A wireframe is a sketch of the page structure drawn with grey blocks and placeholder text — it only cares about what sits where and how much room it takes, not about looking good.

✏️ Why always draw the wireframe first?

1. Changes are cheap. Do the visuals before the structure is settled and any rethink means redoing every style.
2. It forces you to think. If you cannot draw the grey blocks, you have not worked out what that block should contain.
3. It is easier to discuss. Show the grey blocks to a teacher or teammate and they will comment on structure instead of arguing about color.

⭐ Key point: settle the skeleton in this order — ① divide into regions (header / body / footer) → ② decide how many columns each takes → ③ fill in the content → ④ style it last.
Common mistake: starting with colors and shadows, then discovering the structure is wrong and throwing it all away.

👉 See it in the case

The case first stacks the six blocks with semantic tags and writes no styles at all — wireframe thinking, in 9.1 Case planning. Lab step 1 is checked on exactly this.

/* Wireframe stage: grey blocks and dashed lines only — occupy the structure first */
.wire-block {
  background: #e8e6e1;
  border: 1px dashed #b8b2a8;
  border-radius: 6px;
  min-height: 60px;
}

/* Structure settled, now swap in the real styles — the skeleton does not change */
.hero { background: var(--c-surface); border-radius: 12px; }

⭐ Key point: going from wireframe to finished page should, ideally, change only the "skin" (color / type size / radius) and never the "skeleton" (columns and order). If you find yourself having to move the skeleton, the wireframe stage was not thought through far enough.

Switch between "wireframe" and "high-fidelity" and compare two renderings of the same skeleton — note that the skeleton does not change at all.
